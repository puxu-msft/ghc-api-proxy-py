# 项目复查原则

## 这是什么

一份**已经付过代价**的清单，用来做定期复查。每条都对应本项目真实发生过、且不止一次的缺陷形态。

**不是 always-on 规则。** 它不该在每次改动时浮现——那样会退化成噪音，而它要抓的东西按定义是「写的时候看不出来、攒一段时间才显形」的。

**不是门禁。** 项目规矩明确禁止把结果检查升级成阻断装置。产物只有三种：判定「没问题」、判定「违背了，这是修法」、判定「违背了但不值得现在修，记入 `deferred.md`」。**判断权留在人手里。**

**命令给候选，不给结论。** 下面每条检索都会打出需要人看一眼的位置，其中一部分看完就排除了。实证：写这份清单时，「重复判定热点」那条命令打出 `translation_driver/responses.py:65-67` 有一处 usage 原样拷贝，看进去发现它在 `from_anthropic_response` 里——读的是 Anthropic 载荷，键本来就对，拷贝正确。**命令没错，它就该把这个位置交出来。**

**条目会退役。** 每条都写明什么结构事实一旦成立就该删。实现基础没了却还留着，比没有这条更糟。

## 一次复查怎么走

对每条原则：跑命令拿**当前**事实（别凭上次记忆）→ 对照「什么算违背」→ 违背了就分「本次能收口」还是「要单独切片」，后者写进 `.dev/docs/<topic>/deferred.md` 并说明不做的理由 → 顺手用条目自带的退役判据判一次它还该不该留着。

违背项与处置要落到某处（提交信息、`deferred.md`、或告知用户）；没违背的条目**不必留痕**。

## `one-reply-fact-one-answer-across-both-reply-modes`

**一个描述「上游回复了什么」的事实，必须由同一段代码判定，无论这次回复走哪种处理模式。**

**范围限定在当前 CLI 所用的 `pipeline_app`**，它对正常上游回复有两种处理模式：

- **live upstream 上的 block-level delivery**（对应请求的 `stream=true`）——经 `assembler.py` 的 `Terminal`。注意术语：下游交付单位是完整的 Anthropic content block，SSE 只是信封，别把它写成语义上的「流式交付」。
- **whole-body 回复**——`pipeline_app.py:313` 先 `response_payload()`（内部走 translator registry 做响应翻译），`:316` 再由 `handler.reply_summary()` 汇总。**顺序是先翻译后汇总**，`reply_summary` 调用的是 `terminal_from_anthropic`，不会下行到 `translation_driver/responses.py`。

仓库里还有一条 legacy 交付链（`src/app/routes/anthropic.py`、`src/app/delivery/`），**本条不覆盖它**——它不在当前 CLI 的正常回复路径上。若哪天它重新上线，这条原则的事实清单与命令都要先扩，不能默认适用。

### 怎么查

```bash
# A 事实清单（内省，不依赖行窗口）
PYTHONPATH=src uv run python -c "
import dataclasses
from app.pipeline.delivery.assembler import Terminal
print(' '.join(f.name for f in dataclasses.fields(Terminal)))"

# B 生产者：含 record() 的调用点与它内部的 append，这是 tools/thinking 唯一可见的地方
rg -n "Terminal\(|\.record\(|tools\.append|thinking\.append|(stop_reason|usage|dialect|seen)\s*=" \
   src/app/pipeline/delivery/assembler.py src/app/pipeline/translation_driver/responses.py src/app/server/handler.py

# C 消费者：两条 absorb 调用点都必须出现（一条 whole-body、一条 block-level）
rg -n "absorb\(|\.reply\b" src/app/server/pipeline_app.py src/app/pipeline/delivery/stream.py

# D 重复判定热点：同一语义在两个文件里各判一次
rg -n "stop_reason|usage" src/app/pipeline/delivery/assembler.py src/app/pipeline/translation_driver/responses.py | rg "=\s|def |if "
```

### 什么算违背

- **某字段只在一种模式下被写。** 另一模式的消费者拿到**类默认值**，而默认值是个断言——它会声称一件没人说过的事。
- **同一语义有两处独立表达式。** 「什么算 `tool_use` 块」「怎么区分可读推理与密封签名」「缓存要不要从 `input_tokens` 里减掉」出现两份，就是漂移的开始：修好一份时另一份不会有人动。
- **分派条件写了两遍。** 「这是哪种上游」若两处各判一次，两种模式可以对同一请求得出不同答案。
- **某条路径没有读取器却仍产出记录。** 空记录与「没读」是两个事实，混同会让下游把「读不出来」当成「回复里没有」。

### 修法方向

分类逻辑放在**记录自身**（`Terminal.record`，当前是 `tools`/`thinking` 的共同分类点，被两个 assembler 与 whole-body 构造共三处调用）；whole-body 侧用同形状构造函数产出同一种记录；分派**派生自单一函数**（现状：`assembler_for` 基于 `dialect_for` 的结果分派，`handler.py`）；没有读取器时返回 `None` 而不是空记录。

回归测试应**断言两种模式彼此相等**，而不是各自对字面量。⚠️ 要确认这类判据真有分辨力——尤其两处修法互相冗余、逐个变异都不红时——**此时加载 `trusting-a-green-result`**，那才是它的地盘，本条只负责指出这个不变量跨两种模式。

### 凭什么在这里

2026-08-20 一场之内同一形状发作三次，每次都由评审或用户事后发现：`tools`/`thinking` 两处各自分类；usage 只在 block-level 那侧换算，导致同一路由因 `stream` 开关给出两套契约、且 whole-body 那套破坏了下游 schema；`Terminal.stop_reason` 的类默认值在「读不出内容」的路径上伪造出 `end_turn`。详见 `.dev/docs/tui/archive-request-log/` 与 `archive-token-accounting/`。

**权重：足以作为暂定复查项执行**——依据是同一机制在三个独立代码点造成了具名缺陷，不是单次印象。**不足以支撑「上面这组命令有召回力」**：它们从未在一次真实复查里被检验过，首次复查应当把「有没有该抓到却没抓到的位置」一并记下来。

### 什么时候退役

两种处理模式在结构上合并成一条、重复推导不再可能产生时；或 `Terminal` 的字段不再进入任何对外契约、只剩单一具名消费者时。**注意分辨**：模式变成三种不是退役条件，是这条更重要了；legacy 链重新上线同样不是。

## `assertions-about-copilot-wire-need-a-recorded-counterpart`

**当一条断言的期望值在声称「Copilot 实际会发什么／会接受什么」时，本仓必须有对应的录制证据；期望值若由本项目自己的合同与逻辑拥有，手写输入是恰当的。**

判别的轴是**期望值归谁所有**，不是「换个上游还成立吗」——后者会误判：路由分支的结果可能随上游能力变化，但它仍由本项目的规范与逻辑裁决，不因此需要录制。

按命题选 ground truth 的一般方法在 `verifying-authoritative-claims`，本条不重写它。**这里只管本仓的复查问题**：哪些断言在声称外部 wire，它们有没有落到 `tests/int/cassettes/` + `tests/int/recorded/`。项目对录制基建本身的约定（为什么拒绝 vcrpy、chunk 边界为何要保留、`from_history.py` 的适用边界）是 always-on 的，在 `CLAUDE.md`，不在这里。

### 怎么查

```bash
# 手写上游结构的候选点，按文件计数排序便于分诊
rg -c --type py 'input_tokens_details|output_tokens_details|"type":\s*"response\.|"output":\s*\[|"content_block":' tests/ | sort -t: -k2 -rn

# 从 cassette 取真实终结事实：按 SSE 帧解 data: 行，不要用正则啃 JSON
python - <<'PY'
import json, pathlib
def terminal_usage(name):
    p = pathlib.Path("tests/int/cassettes") / name
    for it in json.loads(p.read_text())["interactions"]:
        blob = "".join(c.get("text", "") for c in (it["response"].get("chunks") or []))
        for line in blob.splitlines():
            if not line.startswith("data:"):
                continue
            try:
                event = json.loads(line[5:].strip())
            except json.JSONDecodeError:
                continue
            if event.get("type") == "response.completed":
                return event["response"]["usage"]
for n in ("history_responses_stream.json", "responses_web_search_stream.json", "anthropic_to_responses_stream.json"):
    print(f"{n:38} {terminal_usage(n)}")
PY
```

第一条给的是**候选点**，不是完备清单——它按结构键匹配，换一种写法就漏。对每个候选点问那句话：这里的期望值是在声称外部 wire，还是本方合同？

### 什么算违背

- 一个**声称外部 wire** 的期望值，只由手写 fixture 支撑，仓库里没有对应的录制断言。
- 为确认一件 cassette 已能回答的事，**反复**去打真实上游。
- 期望值靠印象写，而不是从录制里读出来。

### 凭什么在这里

同一场里这条线上错了三次：反复实测真实上游（用户裁定「这种任务根本不应该反复实测上游，mock upstream 是最佳测试方案」）；手写了一份 usage fixture，而它的字段结构恰恰是需要被录制的东西——录制证明 `input_tokens` **含**缓存、`cache_write_tokens` 可能整键缺席；以及用纯文本 grep 搜 cassette 搜不到（chunk 存成 `{"text": ...}`），一度误判评审说错了。

同源小实证：给那条录制断言写期望值时，输入侧三项从录制读出、一次命中，唯一凭印象写的 `output_tokens` 错了。**再一次**：本节上一版给的正则提取脚本会在 `input_tokens_details` 处提前截断，输出不是合法 JSON，而我看了输出没发现——现在这版按 SSE 帧解析。

**权重：足以作为暂定复查项执行**——三次命中都有具名后果。**判别轴（期望值归属）本身尚未在真实复查中用过**，首次使用时应留意有没有它判不了的情形。

### 什么时候退役

本项目不再对外部 wire 作这类断言时；或该职责整体迁出本仓时。**cassette 基建被换成另一种录制格式不是退役条件**——那只要更新上面的命令；方法与复查问题都还在。

## `declined-and-adopted-findings-can-share-one-blind-spot`

**逐条处置完一轮评审之后，还要看一遍处置的组合。** 被判「不修」的那个代价，与新加的那个观测量看不见的东西，可能是同一个。

这个缺口**在任何单条发现的范围之内都不存在**，所以逐条把关的评审按定义发现不了它——它出现在两条处置之间。

一般的评审处置方法学在 `adopting-agent-findings`，本条不重写它。**这里只管本仓的复查问题**：`.dev/docs/<topic>/` 的活文档里，判「不修」的行与自称能观测某事的新增量，有没有配成这样一对。

### 怎么查

两条命令分别打出两侧，配对由人来看。**只排归档树，不排 `reports/`**——本仓完整的逐条处置表恰恰在 `<topic>/reports/` 下，排掉它命令就够不着要查的东西。

```bash
# A 判「不修 / 记录即可」的处置
rg -n --glob '!**/archive*/**' \
   -e '记录但不改' -e '记录不改' -e '不采纳' -e '仅备案' -e '记录即可' -e '不补的理由' .dev/docs

# B 自称能观测某事的量：新增计数、判定分级、以及它自己声明的覆盖边界
rg -n --glob '!**/archive*/**' \
   -e '进 incidents' -e '是下界' -e '新增.*计数' -e '这个数就是' .dev/docs
```

⚠️ **`.dev` 以点开头，且在主仓库被 gitignore。** 上面把它写成显式路径参数正是为此——写成 `--glob '.dev/docs/**'` 配 `.` 搜索根会**命中零行、exit 1、不报错**（两个成因都要，单开 `--hidden` 或 `--no-ignore` 任一都不够）。另一处：`'!archive*/**'` 因模式中含 `/` 而被**锚定到搜索根**，只排得掉顶层那一级；要排任意深度必须写 `'!**/archive*/**'`。两处都实测踩过。

量级参考（2026-08-20 实测）：A 打出 28 行 / 8 个文件，一屏之内可人工配对。其中十余行来自评审本条目的那份报告——**一份讨论这条命令的文档会成为这条命令的噪音**，看到自指命中直接跳过。

对每个 A×B 组合问一句：**B 能看见 A 里被放弃的那个代价吗？** 看不见，就说明这一轮的处置合起来留了洞，而每一条单看都成立。

### 什么算违背

- 一条处置判「这个代价不修」，另一条处置新增一个观测量并声称它覆盖同一片领地，而该量**结构上看不到**那个代价。
- 一个决定 `ok`/`fail` 的量，其盲区没有写在判定旁边——读者据它结案，而它只说得起「没抓到」。
- 处置表逐行都有理由，但没有任何一处记录**组合起来之后**还剩什么没被覆盖。

### 修法方向

不是去补探测点把量做成完备的——那多半做不到，且会让它更像总数。**把量的边界写在它旁边**：非零意味着什么、零**不**意味着什么、哪一侧会多报。若某个被放弃的代价确实需要看见，那是一条独立的新工作，不是给旧量加分支。

### 凭什么在这里

2026-08-20 的优雅关闭一线：评审 4.4 报「关空闲 keep-alive 连接会让在途字节变成 RST」，判**不修**（关任何 keep-alive 连接的固有代价，ROI 不明）；同一轮 5.5 报「被拒绝的请求不留痕迹」，判**采纳**，新增 `refused_requests` 计数。两条分开看都成立。合起来的效果是：**被判为不修的那个代价，恰好就是新计数看不见的那个代价**——RST 掉的请求从不经过闸，因此从不计数，而收尾行读作 `[ OK ]`。是第三轮评审在审「回应评审后又改的那批」时才指出来的，前两轮逐条把关都没有、也不可能发现。

同一事故里还有**同形的第二次**：S-4 报「另三处关连接的地方同样在丢字节」，判**不补**（`client-side/README.md:78`）；而 `severed_connections` 恰恰看不到那三处（同文件 `:61` 自陈是下界）。所以这条不是单次实证。

**权重：足以作为暂定复查项执行**——依据是同一事故内两次同形，且这个缺口的**类型**特殊：它落在任何单条发现的范围之外。但要说准是哪种「多派评审」不管用：**对同一批原始发现再多派几个评审不解决它；把评审对象换成「处置之后的状态」才解决**——本例正是被第三轮增量评审这样抓到的。前两轮没发现，第一轮是因为计数当时还不存在，第二轮（复算变异声称）是**范围之外**，不是逻辑上不可能。

**不足以支撑「上面这对命令有召回力」**：写这条时只验证过 S-4 那一对能被配出来（A `:78` × B `:61`）；**立条讲的 4.4×5.5 那一对是靠人读原件发现的，不是命令配出来的**（4.4 那行在 `reports/260820-graceful-shutdown-admission-deadlock.md:160`，扩大范围后命令才够得着它）。首次真实复查应记下有没有该配对却没配出来的组合。

### 什么时候退役

**可用的结构事实只有一条**：本仓不再用 `.dev/docs/<topic>/` 承载逐条处置表、或不再采用「采纳／不采纳」这种逐条形式时。

「评审处置不再产生这两类并存的结果」**不是**合格的退役条件——它唯一的可观测形态是「连续几次跑 A 或 B 得到空」，正是本文件「退出的判据」明令排除的那种依据；只能当作发起退役复核的弱信号。

**评审轮数变多不是退役条件，是这条更重要了**——轮数越多，处置越碎，组合面越大。

## `a-broken-test-needs-its-scenario-and-expectation-rechecked`

**一条既有测试因产品改动而变红时，要重新观察它的场景与期望是否都该更新，而不只是问「断言还对吗」。**

变红只说明「实现与这条测试的某处对不上」。对不上的可能是断言、可能是期望、也可能是**场景本身从来就没产生过它自称的前提**——最后这种情况下，它此前的绿来自别的东西，而那个别的东西往往正是缺陷本身。

### 怎么查

不需要等到有测试变红。定期查的是**已经发生过的这类改动**：同一提交里既改了产品行为、又改动（不是新增）了既有测试。

窗口锚到**上次复查那一点**，不要用固定时长，也不要用固定条数。理由是实测的：本仓 2026-08-20 四小时推进 59 个提交；同日按不同窗口跑这条命令，候选提交数为 30 天 131 个、7 天 105 个、2 天 71 个——**没有任何固定时长能落在一屏之内**，而固定 `-N` 一天之内就会缩到只覆盖一两小时，那时「输出为空」几乎必然是采样太窄而不是做法消失。所以复查时把上次的锚点记下来，下次从那里起算；首次复查会有一大批积压，照实分诊。

```bash
SINCE=${SINCE:-'2 days ago'}   # 换成上次复查的 commit 或日期
for c in $(git log --since="$SINCE" --format=%h); do
  files=$(git show --format='' --name-only "$c")
  echo "$files" | rg -q '^src/' || continue
  changed=$(git show --format='' --name-status "$c" | rg '^M\s+tests/.*test_.*\.py$' | cut -f2)
  [ -z "$changed" ] && continue
  echo "  $c $(git log -1 --format=%s "$c" | cut -c1-56)"
  git show --format='' -U0 "$c" -- $changed | rg '^-\s*(assert|def test_)' | sed 's/^/      /' | head -3
done
```

两处已知的静默漏检，今天都无害但值得知道：`$changed` 未加引号、靠词分割成多个路径，路径含空格会碎；`git show --name-status` 对 **merge commit** 默认不输出 diff，于是 merge 会被跳过——本项目集成用 squash，若哪天引入 merge 要改。

打出来的多数是正当的（改名、措辞、契约本身变了）。**优先看两种**：整个 `def test_...` 被删掉的；以及断言没动而**夹具动了**（路由、请求体、时序）——后者不会出现在上面的 `-assert` 里，要点开 diff 才看得见，命令只负责把提交交出来。

### 什么算违背

- 一条既有测试**的场景（打哪个路由、发什么 body、什么时候发信号）被改了**，而没有任何地方记下它此前的绿来自什么。纯断言侧的改名与措辞调整不触发——「怎么查」打出的多数正是这一类。
- 修改集中在断言，而场景（打哪个路由、发什么 body、什么时候发信号）原样保留——若原场景产生不了该契约的前提，改断言只是让它换一种方式空转。
- 改完之后，**该层不再有任何测试守这件事**。夹具重写尤其容易这样：把一条「碰巧在真实进程层守着某缺陷」的测试改成进程内的干净版本，守卫就随夹具一起搬走了。

### 修法方向

先判定原测试的绿来自哪里，再决定改什么。**若原场景本身是有价值的（哪怕期望写错了），保留场景、换上正确期望，另立一条**，而不是把场景一起换掉。改完问一句：这一层还剩几条守着？只剩零条就是把守卫搬走了。

⚠️ 判断改写后的那条**还有没有分辨力**（怎么变异、怎么安全还原）是 `trusting-a-green-result` 的地盘，本条不重写它——这里只负责指出「场景可能从来没成立过」这个方向。

### 凭什么在这里

2026-08-20：`tests/int/test_standalone_process.py::test_a_half_sent_request_holds_the_drain_until_the_operator_escalates` 在优雅关闭修复后变红。它断言「进程 3 秒后还活着」——而那**正是死锁的症状**。实测确认它的夹具产生不了它自称的前提：发的 `POST /health/liveness` 打在只注册了 GET 的裸 FastAPI 上，Starlette 只看 headers 就回 405、从不读 body，所以从来没有「还在到达的请求」。它此前的绿来自准入闸死锁本身。

第二层由独立评审补上：我改夹具让它真能表达契约，而那样**等于把「真实进程层唯一会因死锁复发而变红的守卫」一并搬走**（变异实测：改写后的版本对该缺陷完全不敏感）。最终处置是保留原场景、换上正确期望，另立一条。

**权重：单次实证，但两层各自具名，足以作为暂定复查项执行。** 第一层（绿来自缺陷）由 405 探针直接证实；第二层（守卫随夹具搬走）由变异实测证实。**不足以支撑「上面这条命令有召回力」**：它按「同提交改 src + 改既有测试」定位，对「夹具变了但断言没变」只能交出提交、交不出位置，且从未在真实复查里用过。

### 什么时候退役

本仓不再有随产品改动而改写既有测试的做法时（例如全面转向只增不改）。**「最近几次改测试都很正当」不是退役条件**——这条抓的正是看起来正当的那些。

## `a-setting-says-what-it-bounds-not-what-follows`

**一个配置项的说明只讲它约束什么；它击发之后会发生什么，属于决定那件事的机制，不挂在这个键名下——尤其不得推给用户亲笔的契约面。**

本项目有两个并存的面：`docs/.human-controlled/` 是用户亲笔的契约面，我不得修改；代码注释、`docs/`、`.dev/` 是我的实现面。实现事实（有几个执行点、为什么抛这个异常类型）写在我的面上是本分；把它推到契约面上，等于给用户的键加上他没有要求的约束，而那个约束还会被下一个读者当成契约执行。

2026-08-20 同一处触碰三次：`upstream_request_deadline` 的语义只有一条——单次上游尝试的最大存活秒数。它需要两个执行点纯属实现（`await send` 在响应头就返回，body 在 driver 之外流）。我把这讲成「双重身份」，**建议用户写进他自己的 `config.example.yaml`**；同一片改动里，driver 的 docstring 又写了「which is retryable」「nothing has been shown to the client yet」——后者是替下游宣告结局，而结局由 `upstream_request_retry` 那边的配置决定。

**来源那一层也要记**：「这个双重身份必须写进注释」原是子智能体报告里的处方（`docs/tmp/260820-research-upstream-timeout-wiring.md:251`）。我逐字转达，没有裁决**它该落在哪个面上**。评审给的处方要先判落点。

### 怎么查

找「键名附近出现下游结局词汇」的位置。命令给候选，读一眼多数会排除——一段明确写着「由 X 决定，不在此声明」的免责也会被抓出来，那是正确行为。

```bash
rg -n --fixed-strings -B4 -A4 \
  -e 'upstream_request_deadline' -e 'response_header' -e 'stream_idle' \
  -e 'buffering_policy' -e 'proactive_rate_limiter' -e 'reactive_rate_limiter' \
  src/ -g '*.py' \
  | rg -in 'retryable|retried|retrying|continuation|client (sees|gets|is left|would)|重试|客户端|半截'
```

契约面那一侧不靠命令查——它由「我有没有提议往那里加话」触发，而提议出现在会话里，不在文件里。判据是一句自问：**我要加的这句，讲的是这个键约束什么，还是它击发之后会怎样？** 后者一律不进 `docs/.human-controlled/`，也不进 `.dev/human-controlled-docs-candidates/` 的提案。

**正样本对照（2026-08-20 实测）**：把命令指向修复前的 `base.py`（`git show <fix>~1:src/app/pipeline/direct_driver/base.py`），命中那句 `which is retryable, because … nothing has been shown to the client yet`；指向修复后，命中的是它的免责版本。命令确实能抓到这一类，也确实需要人读一眼。

### 什么算违背

- **契约面**：`docs/.human-controlled/**` 里出现（或我提议加入）描述「击发之后会怎样」的句子，而不是「这个键约束什么」。
- **实现面**：一个守卫的注释断言下游结局——客户端看到什么、会不会重试、会不会续写——而那件事由别的配置决定。
- 把一个键的**执行点数量**说成它的**语义**（「双重身份」「两种角色」）。执行点是实现，语义只有一条。

不触发的：在实现面如实写「这里只能管到哪一段、另一段由谁管」——那是本函数的边界，不是下游的结局。

### 修法方向

把句子拆成两半：「这个键约束什么」留在键名下；「击发之后发生什么」移到决定那件事的机制的文档下，或改写成明确免责（「由 X 决定，不在此声明」）。

⚠️ **撤回时只撤落点，不撤事实。** 2026-08-20 认错之后我顺手把实现事实也从自己的代码注释里删了——落点选错不等于这件事不该记。用户当天明确指出这个区分：反馈可以进我控制的代码或文档，错的是想让它进用户控制的权威文档。

### 凭什么在这里

依附本项目的结构：存在一个用户亲笔、我不得修改的配置契约面，与我的实现面并存。没有这个分层，这条判据无从谈起。

同一事故内三次同形（提议进契约面、docstring 断言可重试、docstring 断言客户端未见字节），且第三次是在我已经认错之后由过度修正造成的——满足「一次但代价足以让人记住」。

### 什么时候退役

`docs/.human-controlled/` 不再作为独立契约面时（配置说明改由代码生成、或该目录取消），本条的结构前提消失，连同实证移进 `.dev/docs/<topic>/archive-*/`。
