# Project development workflow

## Delivery style

- This is a new project. New functionality does not default to TDD. Implement a runnable skeleton and happy path first, add a discriminating smoke test, squash it into `main` promptly, then add error handling and regression coverage in subsequent small slices.
- **Never bypass the Spec. This is not negotiable, and it has two halves that fail the same way.** (a) Implementation must not change observable behavior ahead of the Spec — the complete behavioral Spec comes first. (b) A Spec-level fact must not come to rest anywhere except the Spec: not a deferred ledger, not a review report, not a code comment, not a status document, not a message to the user. Either way the Spec stops describing the system while continuing to be cited as though it did, and every reader in between is handed an authority its own author already knows is wrong. **The destination never excuses it, and neither does the reason.**
- **The Spec is a living document and is never frozen** — this is what makes (b) always possible. When a new user ruling, measurement, or finding contradicts or qualifies any part of it, amend the Spec at that moment; never treat a Spec's age, its status line, or a pending question elsewhere as grounds for leaving a known-wrong sentence standing. Every amendment is logged in the Spec's own revision record — what changed, why, and what triggered it — and that record is what makes a living Spec auditable; it replaces freezing as the way to answer "what did we commit to when this code was written". Never describe a Spec as frozen, and never cite one as "the frozen spec": the authority is always the current Spec. Implementation plans are living on the same terms — drafting a plan starts implementation rather than pausing it, and a plan that reaches independent review consensus needs no additional approval before execution. Starting implementation never means the plan or the Spec is closed.
- **The tell for a bypass, learned the expensive way.** You are *already* making the change, and the artifact you are editing is not the Spec. Measured 2026-08-24: a measurement showed `error-envelope/spec.md` §6.2 asserting a retry basis that did not hold for the primary client, and the correction was filed as deferred entry E-9 "pending a ruling" — while that same Spec's own header said clause-level amendments to *derived mapping tables* go by review consensus rather than a user ruling, precisely because those tables are the agent's own derivation and not the user's decision. **The authorization was already there, inside the document being bypassed, one paragraph below the word used as the excuse.** Read who a Spec says may amend what before concluding you may not.
- Distinguish that from the case that genuinely is not yours: when adopting a finding would **change** something the *user* ruled — a ruling, an ADR, an external contract — that is the user's call and you ask first. Correcting your own derived table to match a measurement is not that, and neither is recording a fact the Spec did not yet know. When the **implementation** deviates from a ruling the Spec correctly records, the Spec is right: escalate the deviation, never amend a Spec to match code that drifted from a decision. **Asking is not a place to park a correction** — if the answer is "the Spec is wrong", the Spec gets fixed, not the ledger.
- "Never frozen" is about **Spec documents**, not about content. An invariant the user has ruled on may still be called frozen — `docs/.human-controlled/config.example.yaml` does exactly that for the keepalive terminators, and that wording is the user's and stays. What is forbidden is a *document* declaring itself closed to amendment, or being cited by a freeze date instead of by its current content.
- When something transcribes a Spec — a hand-copied acceptance oracle, a table mirrored into a test, a constant restating a Spec value — amending the Spec obliges you to update the transcription in the same change. A living Spec turns every transcription into a thing that can silently fall behind, and a stale transcription keeps its tests **green** while it does. If a transcription cannot be kept in sync mechanically, say in the Spec clause which file transcribes it.
- Complete and integrate each self-contained small patch immediately. Do not wait for a large feature or design batch when a smaller slice is already reviewable and useful.

## Parallel work

- Parallelism is a core practice, but the development machine is resource-constrained. Keep no more than 10 subagents in flight at once.
- Dispatch narrow tasks immediately when they are independent. Reuse existing reports, verified facts, exact commits, and concrete paths in dispatch prompts instead of making each agent rediscover the project.
- Do not let a new idea silently redirect or narrow the primary task. Run independent work in parallel where possible.

## Tests and review

- Tests cover the critical path, happy path, and failure mechanism actually changed in the current slice. Add targeted tests when a real new failure surface is found; do not prebuild a complete state space, exhaustive proof matrix, or verification governance layer.
- Test groups with different goals get different entries. Setup that only one group needs must live with that group, never in a shared `conftest.py` or a root-level environment tweak — a shared entry imposes one group's environment on every other group and silently removes the next group's ability to choose its own. TUI tests live in `tests/tui/`, are excluded from the default sweep, and run when `src/app/observability/tui.py` changes or by hand via `uv run pytest tests/tui`.
- Upstream behaviour is recorded, not imagined. A hand-written stand-in encodes what we believe upstream does, and that belief is what hides defects: streaming on the primary path returned zero bytes in production while 1243 tests were green, because no fake reproduced Copilot changing an item's id between `output_item.added` and `output_item.done`. When a test depends on how upstream actually behaves, replay a cassette from `tests/int/cassettes/` via `tests/int/recorded/`; re-record with `PYTHONPATH=src:tests/int uv run python tests/int/recorded/record_cassette.py <scenario>`, which needs credentials and makes real calls. Cassettes preserve chunk boundaries because the delivery layer works a block at a time — this is why vcrpy was rejected (`.dev/docs/test-infrastructure/reports/260818-vcrpy-poc.md`). Prompts stay trivial; credentials and account identifiers are scrubbed on the way to disk but never on the way through. Scrubbing works by field name at any depth and covers SSE payloads, and response headers are an **allowlist** — a denylist let three separate identifying headers through, one per round of reading a capture by hand. A cassette also records *whether* a request was authenticated, and the few request fields that decide whether its answer still applies, so a replay notices when the code stops authenticating or starts asking for something else.
- Prefer deriving a fixture over making a call. `tests/int/recorded/from_history.py <scenario>` builds a cassette from the existing service's own capture in `~/.local/share/copilot-api/history-v3*.db`, needing no credentials and no upstream; it stops being an option for traffic after 2026-08-15, when that service stopped storing frames. Two traps, both already hit: history stores each event again for every client-side transform that rewrote it, so taking all of them yields a stream where every event repeats three or four times — and those copies have been through `rewrite-out:responses-fix-stream-ids`, the existing service's own repair for the id instability, which is exactly the behaviour a fixture is wanted for. Keep the roots of the transform graph and nothing else. A derived cassette carries one frame per chunk and says `source: history:<db>:<operation>` for that reason; how the bytes actually fell on the wire is a question only a live recording answers.
- Reuse existing tests and simple probes. For a small fix, run targeted tests. For a squash candidate, run one final full regression, Ruff, and Pyright. After several related slices land, perform one merged-state review rather than repeating full reviews after every micro-commit.
- **Ruff here means `ruff check`. Do not run `ruff format`** — not on the repository, not on a single new file. Ruled 2026-08-18 after measuring what it would actually do: `ruff format` leaves prose alone (0 comment lines touched, identical AST across 219 files) and mostly *removes* hand-written line breaks, which suits this project, but 19 of its 27 splits wrap a long boolean or comparison in parentheses and put the operator at the start of the next line, and that shape was rejected. It has no configuration to disable that shape, and raising `line-length` does not reach it (120 still splits 22 places). Many arguments — four or so upward — one per line is fine and is what `history/sqlite/writer.py` now does; two arguments exploded one per line is not. Formatting a new file on its own is worse than either choice, because it creates a second style with nothing to maintain it.
- Review the final candidate HEAD once by default. Re-review only when the candidate changes in a way that can invalidate the verdict. Do not repeatedly review unchanged bytes or rerun identical evidence without a concrete reason.
- Solve the requested task before building proof infrastructure. **When writing acceptance criteria, a gate list, or an oracle, read skill `writing-acceptance-criteria-that-can-fail` first** — it holds the criteria-side practices (cross-source oracle, both controls per criterion, each evidence tier declaring what it may not impersonate) and the failure shape this rule is guarding against. On conflict this rule wins. Ordinary implementation, refactoring, documentation, migration, Git cleanup, and result checks must not be expanded into manifests, voting systems, graduation protocols, proof control planes, or validation state machines unless the user explicitly requests that infrastructure or it is the deliverable.

## Git and worktrees

- Work incrementally in isolated worktrees when useful. Integrate with a squash commit only; do not use fast-forward or regular merges for feature worktree integration.
- After a reviewed source is squashed and the main-side gate passes, preserve its reviewed source commit under an immutable `archive/YYMMDD-<topic>` branch. Do not point the archive at the squash commit.
- Keep active or dirty worktrees. Remove a clean historical worktree only after its exact HEAD is reachable from a durable archive ref and its semantics are present in `main`.
- Never push or otherwise publish unless the user gives a current explicit instruction for that publication.

## Documentation and agent reports

- Development documents live in `.dev/docs/`, one directory per topic. A topic's living documents (`README.md`, `spec.md`, `status.md`, `plan.md`, `deferred.md`, …) sit at the topic root; its report originals sit under `<topic>/reports/`; finished work is rewritten into `<topic>/archive-<subtopic>/` with the originals kept verbatim in that archive's own `reports/`. `.dev/` is ignored on `main`; its durable source is the dedicated orphan branch `origin/dotdev`, which carries only `.dev/`. The active working copy exists **only at the main worktree root** — an isolated feature worktree has no copy, so work done there still writes reports into the main worktree's `.dev/`. Persist owned paths through a dedicated `dotdev` worktree and exact pathspecs; never switch the shared main worktree to that branch or bulk-copy peers' in-flight files. Commit there freely, but push only with a current explicit instruction; `.dev/README.md` owns the synchronization procedure. The main repository's `docs/` now holds only `docs/.human-controlled/`, which the user writes.
- Subagent investigations, reviews, and PoCs exchange full reports through repository files. New reports use a `YYMMDD-` prefix and are never overwritten: file one under the owning topic's `.dev/docs/<topic>/reports/`, or under `.dev/docs/tmp/` when the topic is not yet clear. **Do not create `docs/tmp/` or `docs/agents/` again** — both were emptied into `.dev/docs/` on 2026-08-21 (`.dev/docs/docs-tmp-migration/`). A branch that predates that date still carries both directories in its tree and the older version of this rule, and a squash takes its tree — so integrating one reintroduces them silently, with no conflict and no error. After integrating such a branch, check that `docs/` holds only `.human-controlled/`. Distil current conclusions into living documents promptly; do not let a report become the only source of truth.
- A report original is a point-in-time record. The paths and line numbers inside it are a snapshot of where things were at that commit, and rewriting them to match a later layout falsifies the record — repoint living documents when files move, and leave archived reports alone.
- Specs are normative **and** living — these are not opposites, and writing them as a contrast is what produced the frozen-Spec rule in the first place. A Spec stays normative while its external contract is active, *and* is amended whenever a ruling or finding changes what that contract should be; it is the combination that makes it worth citing. Implementation and readiness documents are living on the same terms and are updated at meaningful checkpoints, not after every commit.

## Current project priorities and product boundaries

- The primary product path is Anthropic Messages input served through an OpenAI Responses upstream. Continue tracking relevant changes in `~/src/copilot-api-js` and its references, but do not copy its defaults or defects as project contracts.
- Block-level buffering is required. Downstream does not provide token- or event-level live streaming; a complete Anthropic content block is the delivery unit.
- The project uses its own versioned reasoning carrier as the default producer and accepts the current `copilot-api-js` v1 format on its legal compatibility path. Compatibility does not require matching every malformed decoder edge or copying lossy aggregation.
- The deployment goal is a systemd/cgroup-managed service with listener continuity and graceful shutdown. Socket activation preserves the listener and queued, unaccepted connections; it does not migrate connections already accepted by the old process and must not be described as full zero-downtime migration.
- Production replacement of the existing `copilot-api-js` requires a separate explicit cutover instruction. Until then, do not signal, stop, restart, or take over the existing `4141` Bun service.
