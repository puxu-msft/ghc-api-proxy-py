# Taste
- When reporting problems or findings, don't lead with low-level code/implementation detail; the user says that level is something they cannot advise on. Explain what the issue means in terms of user-visible effect/impact and state what the correct approach should be. Confidence: 0.85
- Communicates in Chinese and expects responses and deliverables (reports, status, handoffs) in Chinese. Confidence: 0.7
- Design/spec-first then implement: when asked to add or fix a capability, first refine the design or living spec (and surface whether the feature already exists), then do the implementation. Confidence: 0.75
- When a defect is blocking real usage, prefers a minimal targeted stopgap fix first ("先止血") over blocking on the broader spec/redesign — the fuller design work comes after the bleeding stops. Confidence: 0.65
- At session closeout ("收尾"), explicitly verify that session-created temporary worktrees, branches, and tmp directories have been cleaned up. Confidence: 0.75
- Wants behaviour-changing knobs exposed as explicit, opt-in config fields (descriptive snake_case booleans, default `false`) that layer on top of a canonical default, rather than implicit hardcoded behaviour — and expects the field names they specify (`add_header_*` style) to be used verbatim. Confidence: 0.6
- Prefers defaults that follow the protocol/standard's canonical mechanism (applied uniformly by protocol, not by provider), with provider-specific quirks handled by opt-in overrides on top. Confidence: 0.6
- Expects the agent to build complete, self-sufficient mechanisms and only escalate genuine product decisions — internal/process details (e.g. how learning/refinement is done) should not be pushed back as questions to the user. Confidence: 0.65
- Gives terse, high-level directives and expects them executed end-to-end — including discovering the applicable project conventions and doing all follow-through (e.g. updating references after moving files) — without asking for confirmation. Confidence: 0.55
- Prefers experiment/probe artifacts isolated from the main repository tree in a dedicated dev area (e.g. a `.dev/` mount ignored by the main repo) rather than committed at the repo root. Confidence: 0.5
- When told to commit ("提交你的相关改动"), expects only the agent's own changes committed: other in-flight/peer work in the same repo — even inside the same file — must be left untouched, staging just the agent's lines into the index (e.g. a single-hunk patch applied with `git apply --cached`) without modifying the worktree. Confidence: 0.8
- Before committing, verify the staged set matches the expected scope exactly and abort if it deviates (e.g. abort when the staged entry count isn't the expected number, or when any staged path falls outside the intended directory), plus re-check after committing that peer WIP is intact. Confidence: 0.65
- Keeps work local: commits are made but not pushed unless explicitly requested. Confidence: 0.5
- For config values naming operator-provided data (model metadata, tokens, auth state), prefers a separate data file pointed to by an explicit path field over inlining the data in config; expects such path fields to support `~`, `$VAR` and `${VAR:-fallback}` expansion, with relative paths resolved against the config file's directory. Confidence: 0.65
- Prefers filling an upstream's data gaps with locally bundled/curated data (e.g. a shipped metadata file) rather than accepting a bare upstream catalog, and defines the merged result as the **intersection** with the upstream list — only what both sides name is served. Confidence: 0.6
- Once a one-off/ad-hoc script produces a durable artifact (e.g. a generated snapshot file), wants it promoted to a committed, reusable in-repo tool rather than left as throwaway shell commands — placed following existing repo precedent (inside the relevant package, exposed via `__main__`/`-m`, with CLI-surface tests). Confidence: 0.5
- When the user floats a placement/approach suggestion (e.g. "放到…包内你认为合适吗"), expects the agent to check it against existing repo conventions and come back with a reasoned answer — including disagreeing with concrete precedent as evidence — rather than comply silently. Confidence: 0.5
- Prefers literal, visible references in config over implicit resolution magic (rejected a short-name-in-path shorthand because a field named `*_json` would then accept a bare name); which data source is active must be readable as a fact from the config. Confidence: 0.55
- For point-in-time samples/snapshots (e.g. a captured model-info file), wants the sample date in the filename (`opencode-go-20260916.json`) so newness is visible from a directory listing, and is fine with the config path pointing straight at the dated name — accepting that re-sampling means updating the path and restarting rather than keeping a stable reference. Confidence: 0.55
- Treats provenance/staleness (ages, dates, verification state) as advisory, not gating: prefers a warning in logs plus a status endpoint over refusing to start, so a stale-but-usable deployment keeps running; and unknown state must be reported as unknown (null) rather than a default value that reads as "verified" or "fresh". Confidence: 0.5
- Permits the agent to directly edit the live runtime config (and restart the service to verify) rather than leaving config changes as instructions for the user to apply. Confidence: 0.7
- Prefers install-location-agnostic config references for bundled data: shipped files should be referenced via a package-location variable (e.g. `${GHC_PACKAGE_DIR}` resolving to the installed package itself) so the same config works from a checkout and under uvx isolation without copying files, rather than checkout-relative or absolute data-dir paths. Confidence: 0.85
