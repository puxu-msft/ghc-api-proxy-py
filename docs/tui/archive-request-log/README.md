# 档案：每请求一行的日志

`[ OK ] 09:02:14 H1/H2 200 anthropic-messages/gpt-5.6-sol 51.6s ↑964.6KB ↓475.4KB …` 这一行。2026-08-19 至 08-20 完成。

行为契约见 `../spec.md`；本文件记录**怎么定下来的**和**踩过什么**。

## 零、最该记住的一条：先证明你要建在其上的平面存在

footer 的每一部分都写完并测过之后，用户在终端跑起来，**什么输出都没有**——连启动信息都没有。

原因不是 footer 坏了，是**它挂靠的日志流根本不存在**：没有人调用 `setup_logging()`，uvicorn 起时 `log_config=None`，而服务链路里没有任何地方发出过每请求日志。我此前假定它存在，依据只是 `logging.py` 里有 `[ OK ]` 这样的前缀常量。

「有 processor / 有前缀常量」不等于「有人在发这种日志」。修法是顺着真实入口（`cli.py → serve → request`）把流程从头读一遍，并**把程序跑起来**。这条教训已沉淀为记忆条目 `verify-the-surface-exists-before-building-on-it`。

## 一、行的形态

沿用 `copilot-api-js` 的字段顺序，两处刻意保留：

- **成功**的行把 method 与 path 收成 `<inbound-format>/<model>`——请求既然成功了，哪个模型应答才是值得读的，路由是噪音。
- **失败**的行保留 `METHOD /path`——那是要被复现的东西。

字段顺序：协议对 → 状态码 → 主语 → 耗时 → 线上字节 → 词元 → 结束原因 → 重试 → 推理块 → 失败原因。从「怎么样了」收窄到「花了多少」再到「为什么结束」。每个字段在无话可说时整个省略，所以一次裸拒绝和一次完整流式应答共用同一套列序，而不是分裂成两种格式。

`↑`/`↓` 同时用于字节和词元，靠单位区分：字节带 `B`/`KB`/`MB`，词元是裸数字加 `k`/`m`。

## 二、这一行描述的是 proxy ↔ upstream 那一段

用户裁决（2026-08-19）：**日志行与 live footer 显示的都是 proxy 与 upstream 之间的情形，除非报错原因是客户端断连。**

具体后果：

- `↑` 是**实际发往上游的字节**，取自 httpx 真正送出的请求，而不是客户端 body 的大小——翻译会重写载荷，被计费和被词元化的是发出去的那一版。
- `↓` 是**从上游收回的字节**，不是转发给客户端的量。两者在任何重写发生后就不同。
- 一个在到达上游之前就被拒绝的请求**两个方向都不报**：它没有上游交互可描述，在那里印客户端侧的尺寸等于凭空发明一段从未发生的对话。

## 三、着色：颜色承载含义，不做装饰

完整规则见 SPEC 的着色表。这里只记不显然的判断：

- **只有回来的那半升级量级**。上行字节大是长上下文的常态，把它染色等于每行都在喊。
- **「普通」那一档不着色，而不是显式白**。`\x1b[37m` 把前景设成调色板的白，多数深色主题里它比终端**自己的默认前景更亮**，于是最普通的一档反而比根本没被碰过的字段还响，读起来像加粗；它还隐含假设深色背景，浅色终端上接近不可见。**耗时保留显式白**（用户指定），因为那里的白是一条通往黄、红、加粗红的阶梯的底端，是一个档位而不是「正常」的说法。
- **结束原因是阶梯不是标志位**：`end_turn`/`stop_sequence` 绿、`max_tokens` 黄、`refusal` 红（用户裁决）。这几个都终结了这一轮，单一颜色只能表达「它停了」——而这件事有这个字段本身就已说明。绿色必须保住「这里没什么可看的」这个含义。`tool_use`/`function_call` 不进任何一档，它表示这一轮**还在继续**。
- **`AskUserQuestion` 从灰色工具列表里挑成青色**：这个工具的用途就是向人提问，工作此刻卡在「有没有人看到」上。对列表里其它名字**不作任何断言**——工具名是任意字符串，别的工具同样可能在等审批。
- 工具名按**颜色分段**着色而不是逐个着色，否则灰名字之间会夹着白逗号。

### 已接受的瑕疵：舍入带内同数字异色

`format_bytes` 只印一位小数，阈值又取整数 `10 * 1024`，所以 10239 与 10240 都显示 `10.0KB` 却分处「灰」与「不着色」两侧。

我曾改成按显示数字着色以消除这个矛盾（阈值实际前移约 51 字节）。**用户否决**：「你过于纠结『换来屏幕上不可能自相矛盾』了……不必移动阈值。」已回退，现为明示的接受项。

这里真正成立的问题是**我的文案与事实不符**（当时源码注释和 SPEC 都声称「颜色与打印数字同时变化」）。正确的修法是改文案，不是改阈值。

## 四、用词跟随上游那条腿

裁决于 2026-08-20。既然这一行描述的是 proxy↔upstream，描述回复内容的字段就用**上游自己的词**：

| 事实 | Anthropic 上游 | OpenAI Responses 上游 |
|---|---|---|
| 推理块 | `think(enc:1,txt:2)` | `reason(enc:1,txt:2)` |
| 以工具调用收尾 | `tool_use(Bash,Read)` | `function_call(Bash,Read)` |

理由：两者足够像会被混淆，而「这一轮到底走了哪个上游」正是有人翻日志要查的东西。Responses 本身没有 stop reason，`tool_use` 是 assembler 为满足**下游**契约合成的——对响应体是对的，对这一行是错的，因为 Responses 的追踪里根本不存在名为 `tool_use` 的东西可供检索。

**判定依据是路由，不是回复体**：缓冲回复是在翻译成客户端形状之后才读回的，那时体内已没有任何东西说明是谁应答的。流式路径由 assembler 自身携带（一个 assembler 只可能描述一种上游）。两者共用同一个分支（`assembler_for` 基于 `dialect_for` 的结果分派），以免两条路径对「谁应答的」得出不同答案。

方言表是**封闭白名单**：表以外的结束原因一律不着色，因为光看名字无从判断是好消息还是坏消息，随便给个颜色就是在断言代码并不知道的事。

## 五、数据来源的收口：展示层读聚合记录，不读原始对象

用户提出（2026-08-20）：要通过中间变量切分依赖，不要让日志直接访问原始请求内容决定显示。

当时的实际状况是一半一半：渲染层本来就是纯的（只吃 `RequestLine` 与注册表快照，不起服务不开终端就能构造），但**缓冲路径在日志点直接翻原始 payload**——自己判断什么算 `tool_use` 块、怎么区分可读推理与密封签名；而流式路径读的是 `assembler.terminal`。

**同一个事实两份实现，可以静默漂移，且修好一份时另一份不会有人动。**

收口方式：

1. 分类逻辑收到记录自身 `Terminal.record()`，三个「块结束」的地方统一调用；
2. 缓冲回复用 `terminal_from_anthropic()` 产出同一种记录；
3. 两条路径都把它发布到公共载体 `RequestContext.reply`。

配套的测试判据是**断言两条路径彼此相等**，而不是各自对字面量——只有前者能让漂移变成失败。变异对照要打两处：共享分类器、以及只打其中一条路径。

### 这次收口引进过一个回归

`Terminal` 的类默认值 `stop_reason="end_turn"` 经聚合记录进入日志行后，`/responses` 入站的每一行都开始**声称一个上游从未说过的结束原因**（改之前那些行不显示结束原因）。这比少显示信息严重——它是无证据的断言。已修，并由 `test_a_route_whose_reply_cannot_be_read_claims_nothing_about_it` 钉住。

顺带暴露一个既存缺陷：`/responses` 与 `/chat/completions` 入站的回复汇总一直是空的（读取器只认 Anthropic 的 `content` 块），记在 `../deferred.md` 第 0 条。

## 六、评审发现过而现在容易忘的几件事

来自 `reports/260819-review-request-log-enriched.md`：

- **count_tokens 端点**当时既不显示模型也不显示词元数——而这两个事实明明都已确定。这个最可能被循环调用的端点曾是整个代理上最不可读的一行。
- **路由后抛错的分支**只填了 resolved model，丢掉了已知的 `alias → claude-model` 映射。一个映射做了意料之外的事，恰恰在它最要紧的那次请求里不可见。
- **字节在交给 ASGI 之前就被计入**，而注释声称那是「实际上线的字节」。

来自 `reports/260820-review-request-log-colouring.md`：

- 字节阈值测试曾是**假绿**：样本里带 `duration_s=1.0`，而耗时字段本身必定是白色，于是 `WHITE in line` 在字节仍是灰的时候照样通过。改成断言完整 span（箭头 + 数字 + ANSI code）后，评审用来证伪的变异会让它变红。
- 「其它每个工具都会自行了结」是**无依据的绝对断言**——工具名是任意字符串。颜色只能建立在「`AskUserQuestion` 把要等人写在名字上」这一点。

着色与用词之外，`../archive-token-accounting/reports/260820-review-translated-usage-and-colour.md` 还指出 SPEC 里有一句「中间档是白色」在改动之后没有同步——同一份 SPEC 的规则表与理由段直接互相矛盾。已修。

## 七、方法论沉淀

- **变异对照要打对地方**。有一次两处保护互相冗余（各自都足以消除症状），于是单点变异全都不红；正确的对照是**同时**移除两者。测试没问题，是我把「修复」和「判据」对错了。
- **不要在共享检出里对可能被并行编辑的源文件做「快照—改—还原」式变异测试**。有一次还原后字节比对为 False，事后核对确认没造成损失，但那是侥幸。应在临时副本或独立 worktree 里做。
- **界面的验收标准是人看着对不对**，测试替代不了。这一块的做法是实现优先、试用验收主体、后补防回归测试。
