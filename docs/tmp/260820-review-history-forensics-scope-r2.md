### 2.2 一个被完全漏掉、且我认为应当补进选项的解读：`debug replay`

r1 与 r2 都把「调研」理解成**读已经发生的事**。但需求盘点里出现频率最高的取证**手段**之一，是**主动对上游发受控探针**——`260820-forensic-demand-audit.md` 至少三处：websearch 400 那次「A/B/C 三组、19 次真实推理请求」、空 text block 那次「E1-E5 五组含阳性对照」、上游能力探针那两份。实测这些目录都还在：`exp/260820-websearch-probe/`、`exp/260820-empty-text-probe/`。

这些探针当时全部是**手写 curl 重新拼请求体**的——因为拿不到我方实际发出的字节（那正是盘点第 1 名缺口）。

而 L2 一旦落地，`UpstreamExchange.request_body` 里躺着的就是**逐字节的真实上行请求**。此时 `debug history replay <id>`（原样重发）与 `replay --edit`（改一个字段再发，即「最小判别实验」）**几乎是免费的增量**——请求体、上游 method/path、headers、authenticated 全部已在 3.1 的表里。

为什么这不是我在发明需求：`websearch-400-our-side.md` 里那道「最小判别实验」是**已经被手工做过一遍**的动作，r1 评审引用的原文说的是「免掉手动跑一遍」。r2 只做到了「不必再手写请求体」，没做到「不必再手写发送」。

**判定：应当补进选项，作为分叉 F 的同级项或分叉 A 的一个附注。粗估 +0.5 片（前置 A2 或 A1）。严重度 minor**——它是增量而非缺陷，但它是六个分叉里性价比可能仅次于 E 的一项，用户看不到就没法要。
**可信度：可据以行动**（三处探针记录与两个 `exp/` 目录均实测）。

### 2.3 会话级聚合：字段采了，能力没给

3.1 把 `session_id` / `agent_id` 列进了 `ForensicRequest`，理由是「否则第四节的 `--session` 过滤器没有数据源」。但：

1. **第四节现在根本没有 `--session` 过滤器**（见 N5，悬空引用）；
2. 除了「按 session 过滤列表」之外，r2 没有提出任何聚合能力——而 `history-system.md` 已 spec 了 `SessionSummary`（request_count / agent_count / token 合计 / 各状态计数 / models 分布）。

对这个项目，会话级聚合的价值是具体的：**它能回答「这次 subagent 工程里，是哪个 agent 的哪几次请求出的事」**——而这正是 r1 评审引用的事件 A 里，当时只能靠翻 3855 份 transcript 才拼出来的东西。

**判定：不必成为第七个分叉**（它是 CLI 的一个子命令，不是架构选择），但 6.1 的分片表应当在分片 2 或 3 里给它一行，否则「采了 session_id 却只能拿来过滤」会成为下一轮的返工点。**严重度 minor。**

### 2.4 分叉描述会不会让人选错

逐个查了六个分叉的选项文本。**r1 那种「反对理由对推荐项同样成立」的硬伤没有了**，这一层做得干净。剩下三处会影响选择：

**(a) 分叉 E 的选项文本断言了一件做不到的事 —— 这是 N1，blocker，详见第四节。** E1 写着「加一个文件 handler 覆盖所有日志行」，而实测这在默认交互模式下不成立。用户会按一个错误的能力描述批准它，而且 r2 还特意说了「若你只想批一件事，批这个」——**最可能被单独批准的那一项，恰好是描述失真的那一项**。

**(b) 分叉 D 缺中间选项，全有全无的成本表本身构成论证 —— N3，major，详见第四节。**

**(c) 分叉 C 的 C3 代价被轻描淡写。** C3「全部 durable」的代价写的是「请求路径会被磁盘抖动波及」。但按 3.3「先写后分类」，durable 的 L3 意味着**每个 chunk 到达都要等一次不可丢弃的入队**——在块级交付的热路径上，这不是「被抖动波及」，是把磁盘写入放进了每 chunk 的关键路径。C3 的真实代价比文本给的严重一档。不过 C3 不是推荐项，且没人会因为低估了「更保守选项的代价」而选错方向——**严重度 minor**，改一句话即可。

### 2.5 一处该说明的正面判断

分叉 B（raw chunks vs `SseEvent`）与分叉 C（持久化保证）都是**评审新增的真分叉**，而不是把设计陈述改写成问句凑数的。B 的差别会改 schema，C 的差别会改接口，两者都是「选错了以后要返工」的量级。r2 把它们提上来是对的。

同样，3.3「先写后分类」用「失败何时可知」取代 r1 的「失败全留 + 成功滚动窗口」，是本版最好的一处设计改动——它指出了一个 r1 与我都没看见的时序问题（进程 crash / 请求永久挂起时，「完成后再决定留不留」恰好丢掉最需要的记录）。这条我认可，**可信度：可据以行动**。

## 三、作为裁决材料是否够用

### 3.1 用户读完第四节能不能直接拍板

**大部分能，但有三处会卡住。**

能拍板的部分：分叉 A（三档深度 + 粗估 + 「能回答什么」列）、分叉 B、分叉 C、分叉 F，这四个的选项、代价、推荐理由、反对理由都齐了，而且都给了片数量级。阅读指引把「直接跳到第四节可以开始裁决」写在最前面，这个设计是对的。

会卡住的三处：

1. **分叉 E 的能力描述失真**（N1）。用户没法在一个错误的前提上做正确的决定。
2. **分叉 D 缺中间选项**（N3）。用户面对「+3–4 片 vs 0」，实际上是在被要求二选一，而真实的选择空间里有一个 +1 片左右的最小只读子集。
3. **附带小项那三条是伪装成附注的真分叉。** 「`ProxyConfig.history` 死开关怎么办」「配置键放哪」「旧链路 history 去留」——第一条明确带来行为变化（默认开始记录），第三条触及「不得擅自删除已实现的功能」。r1 里它们是分叉 C 和 D，有选项列表和推荐理由；r2 把它们压成了三个 bullet，其中「旧链路去留」只剩我的建议而**没有列出选项**。这是降格，不是精简。**严重度 minor**，但对一个「读完就能拍板」的文档来说，把带行为变化的项藏在「附带需要一并示下的小项」标题下面是不合适的。

### 3.2 分叉 D 的表述是否真正把决定权交还了

**大方向上交还了，细节上仍有三处在替用户论证。** 逐条说。

**交还得好的地方**（这些是真的，不是客套）：

- 1.10 单独立节，把 `MAIN.md` 说了什么、以及「没有像 Responses WebSocket 那样标注暂不支持」这个关键对照写清楚了；
- 分叉 D 标题带 ⚠️「需要你亲自裁决」；
- D2 的推荐标记写成「**我倾向，但这是你的决定**」，而不是其他分叉那种「（推荐）」；
- 正文明写「但这个理由不足以推翻你亲笔写下的产品端点清单——r1 那样做是越权，本版改正」。

这四条加起来，已经把 r1 blocker 1 的性质问题解决了。**我不认为这是「换个说法继续论证」。**

**但仍在施加压力的三处：**

1. **成本表是全有全无的**（N3）。D1 +3–4 片、D2 +0、D3 +0。当唯一的「做」选项标价是「不做」的三到四倍，成本表本身就是论证，而且是比文字更难反驳的那种论证。补一个最小只读子集（`GET /entries`、`GET /entries/{id}`，不做 WS、不做 pin/sessions/stats/export，约 +1 片）会显著改变这个分叉的形状。

2. **D3 的代价被高估了。** D3 写着「+0，但**需你改人写文档**」。而 `MAIN.md` 开头自己写着：「你可以建议修改或补充本系列文档，但需要用户裁决。你不能亲自动手修改本系列文档，但可以提供文档或片段，写入 `.dev/human-controlled-docs-candidates/` 目录，供用户参考。」——**也就是说草稿可以由我方备好，用户只需裁决与落笔**。把 D3 标成「需你改文档」，让唯一一个「正式把它标为不做」的选项看起来比 D2 更麻烦，而这两个选项的实质差别恰恰在于 D3 会留下书面裁决记录、D2 不会。**严重度 minor，但它正好作用在这个分叉最敏感的地方。**

3. **D 没说「谁在用」。** r2 说了这些端点当前只在旧链路、新链路够不着，但没说**现在有没有任何东西在消费它们**（按 1.1，旧链路只被测试调用，所以答案大概率是「没有」）。这个事实对用户裁决是正向有用的——它把问题从「要不要砍掉一个在用的功能」还原成「要不要实现一个写下来但从未被使用的端点」，**而这两个问题的答案可能完全不同**。r2 手里有这个事实却没放进分叉 D。**严重度 minor。**

**综合判定：分叉 D 达到了「交还」的及格线，但离「中立呈现」还差一个中间选项和两处成本口径的修正。** 我不会因为分叉 D 拦下这份文档；我会因为分叉 E 拦下它。

### 3.3 信息不足的地方

- **旧库怎么办仍然没答**（N4 的一半）。2.1 与 6.1 说取证库另用独立文件名，那么 `~/.local/share/ghc-api-proxy/history.db` 里那 8,630 行、2.4MB 就那么放着？删？留给旧链路测试继续写？一句话的事，但它是用户会问的第一个操作性问题。
- **CLI 面在 r2 里反而退化了**（N5）。r1 §2.4 有明确的子命令与四个过滤器；r2 把它散在 6.1 表格的括号里，且 3.1 还引用了一个已不存在的「第四节的 `--session` 过滤器」。裁决 CLI 细节确实不必占一个分叉，但用户至少要知道最终会得到什么命令。
- **默认记多少，不再是用户的选择**（N6）。3.3 的「先写后分类」实质上等于「无条件全量采集，事后回收」。这个默认值的行为后果（每个请求都写盘、L3 落地后每请求几 KB）应当至少在附带小项里出现一次，让用户有机会说「不，默认只记失败」。

**几乎没有。** r2 比 r1 长，但增加的部分（1.4–1.9）全是推翻 r1 假设的实测依据，属于必要的。三处可压：

## 四、r2 新增发现

### N1 —— **blocker** —— 分叉 E 的核心断言被现有代码证伪，而它正是最可能被单独批准的一项

**分叉 E 的原文**：

> 实测全项目只有一个 `StreamHandler`，加一个文件 handler **覆盖所有日志行**，不只是完成行。
> 推荐 E1：它是本方案里性价比最高的一项，且**立刻**就能用——不依赖 A/B/C/D 任何一个。**若你只想批一件事，批这个。**

「全项目只有一个 `StreamHandler`」这句是对的（`src/app/observability/logging.py` 的 `logging.StreamHandler()`）。**但结论不成立。**

`src/app/observability/tui.py` 的 `FooterTui.activate()` 里：

```python
previous = list(root.handlers)
root.handlers = [handler]          # handler 是 LiveConsoleHandler
with live:
    try:
        yield self
    finally:
        root.handlers = previous
```

**TUI 激活时把 root logger 的 handler 列表整体替换成它自己那一个**，退出时才还原。任何在启动期装上的 `FileHandler` 会在 TUI 活着的整段时间里**被摘掉**，一行都写不进去。

而 TUI 什么时候激活？`src/app/server/pipeline_app.py` 里 `footer_tui_or_none(chain.active_requests, chain.capabilities)` 后 `terminal.enter_context(tui.activate())`，判据是 `detect_terminal()` 的 `caps.live`——`footer_tui_or_none` 的 docstring 写着「A pipe, a file, a CI job and `TERM=dumb` all get plain logs」，**反过来就是：接着真终端跑的时候，TUI 默认是开的**。

于是失效场景恰好是分叉 E 存在的理由：

- 管道/重定向/CI 下跑 —— 文件 sink 正常工作，但这些场景本来就没有「终端滚动丢失」的问题；
- **接着终端交互式跑（也就是 256.9s 超时那次事故的现场）—— 文件里什么都没有。**

用户按 E1 的描述批准 0.5 片，得到的是一个**恰好在需要它的时候是空的**文件。这比不做更糟，因为下次出事时会有人以为「日志已经落盘了」而不去找别的证据。

**这不是难修**：让 `activate()` 只替换控制台类 handler、保留其余（`root.handlers = [handler, *(h for h in previous if not isinstance(h, logging.StreamHandler))]` 之类），或者让文件 sink 走独立 logger 而不挂 root。但它会改变 E1 的两个数字与一句话：粗估不再是 0.5 片（要动 `tui.py` 并补一个「TUI 开着时文件仍在写」的判别性测试），「覆盖所有日志行」要改成「覆盖所有日志行，前提是先修 TUI 的 handler 接管」。

**为什么定 blocker 而不是 major**：分叉 E 是 r2 明确标注「若你只想批一件事，批这个」的选项，是全文里最可能被单独、立刻批准执行的一项；它的能力描述失真会直接导致一次基于错误前提的裁决，而且失真方向是「以为有、实际没有」。这满足我在 r1 评审里给 blocker 定的口径：按现状裁决会得到与真实意图不符的结果。

**修法**：E1 的内容改为「加日志文件 sink + 修正 TUI 的 root handler 接管」，粗估上调，并在选项文本里写明这个前置。顺带值得在正文提一句：TUI 接管 handler 这件事本身是既有实现的一个隐患（任何未来的 sink 都会踩），不只是 E 的问题。
**可信度：可据以行动**（`tui.py` 的 `root.handlers = [handler]`、`pipeline_app.py` 的激活点、`footer_tui_or_none` 的探测语义均已逐行读过）。

### N2 —— **major** —— `pinned` 是一列没有任何写入途径的字段

3.4 把 pin 当成滚动窗口的兜底：「`pin/unpin` **已实现且已 spec**，是滚动窗口的兜底：手动钉住一条正在排查的记录，免于被淘汰。」

两个问题叠在一起：

1. **「已实现」指的是旧链路的 `HistoryStore.set_pinned`**，作用在 `entries` 表上。而 r2 的 1.5 已经裁决**不复用 `HistoryEntry` / `entries` 合同，新 DTO、新表**。3.1 的 `ForensicRequest` 确实有 `pinned` 列——但那是一列全新的列，旧实现一行都用不上。「已实现」在新表的语境里不成立。
2. **没有任何动作能把它置位。** 6.1 的分片表里，CLI 只出现 `debug history list --json`、`debug history show --json`、`export-cassette`。**没有 `debug history pin`。** 分叉 D 若选 D2/D3（我倾向、r2 也倾向），REST 的 `POST /entries/:id/pin` 也不会有。

结果是：3.4 的容量论证依赖一个用户无法触发的机制。**这恰好是我在 r1 评审里指出的问题的镜像**——r1 是漏了 pin，r2 是把 pin 写进了设计但没给它入口。

**修法**：6.1 分片 2 或 3 加 `debug history pin/unpin <id>`（成本极低，就是一条 UPDATE），并把 3.4 的「已实现」改成「旧链路已有等价实现可参照，新表需重新接一条写入路径」。
**可信度：可据以行动**（1.5 的裁决、3.1 的列表、6.1 的分片表三处对照）。

### N3 —— **major** —— 分叉 D 缺中间选项，且 D3 的代价被高估

已在 3.2 展开，此处只留判定与修法。

- **补 D4**：最小只读 REST 子集（`GET /history/api/entries`、`GET /history/api/entries/{id}`，不做 WS、不做 pin/sessions/stats/export），粗估 +1 片左右。理由：`MAIN.md` 写的是 `/history/api/*` 与 `/history/ws` 两项，一个只读子集能兑现前者的主体，而成本只有 D1 的四分之一。没有它，这个分叉在成本上是全有全无的二选一。
- **改 D3 的代价**：`MAIN.md` 自己允许我方把候选稿写进 `.dev/human-controlled-docs-candidates/`，所以 D3 的代价是「我方备稿 + 你裁决落笔」，不是「需你改人写文档」。
- **补一句事实**：这些端点当前**没有任何消费者**（旧链路只被测试调用）。这把问题从「砍功能」还原成「实现一个从未被用过的声明」。

### N4 —— minor —— 1.5 与 2.1/6.1 在「用不用同一个数据库文件」上直接冲突

- 1.5 结论：「**可以共用同一个数据库文件**与『单 writer + 有界队列 + 线程池下沉』的实现模式，但不该复用 `HistoryEntry` / `entries` 合同。」
- 2.1 建议：「测试库改落 `tmp_path`；或**取证库另用独立文件名**。**建议两者都做**。」
- 6.1 分片 0：「前置：测试库改落 `tmp_path`；**取证库独立文件名**。」

三处里两处说独立文件，1.5 说可以共用。方向上以 2.1/6.1 为准（它们更晚、更具体、且带理由），但 1.5 没跟着改，读者会撞上。

同时，**既有 8,630 行旧库的处置仍然没有交代**（删 / 留 / 归档），这是 r1 评审第 14 条里没被解决的那一半。

### N5 —— minor —— 悬空引用，且 CLI 面比 r1 退化

3.1 写着「否则**第四节的 `--session` 过滤器**没有数据源」。**r2 第四节没有任何 CLI 过滤器描述**——r1 的 §2.4（`list` 支持 `--model`/`--status`/`--since`/`--session`）在重写中被删掉了，引用没跟着改。

后果不只是一个断链：r2 现在**没有任何一处完整描述 CLI 会长什么样**，只有 6.1 表格里括号中的三处提及。CLI 细节不必占一个分叉，但既然 3.1 拿它当字段的存在理由，就得有个地方写着它。

### N6 —— minor —— 「默认记多少」从用户的分叉变成了设计陈述

r1 有分叉 B（默认触发档位：常开全量 / 默认全关 / 失败全留+成功滚动）。r2 用 3.3「先写后分类」取代了它——**技术论证是对的且更强**（失败何时可知），我不反对这个设计。

但结果是：**「默认对每个请求都采集并落盘」这个行为决定，现在没有出现在任何分叉里。** 3.3 是设计陈述，3.4 是容量机制，附带小项问的是「配置键放哪」而不是「默认值是多少」。用户失去了说「不，默认只记失败」的位置。

同时，r1 评审第 16 条（双维度限流继承自未裁决建议）也落在这里：1.8 把压缩口径的依据做硬了，但「双维度」本身仍是设计陈述。

**修法**：附带小项加一条——「L2/L3 的默认档位：全量 / 仅失败 / 失败全留+成功 N 条，以及双维度还是仅条数限流」。一行字，把决定权还回去。

### N7 —— minor —— 限流仍排在分片 6，而 L3 在分片 4 落地

r1 评审第 13 条未解决。3.4 有完整的容量设计，但 6.1 把「配置键、双维度 reaper、档位开关」放在分片 6，而 L3（每请求数 KB 压缩后）在分片 4 就落地了。中间两片期间库只涨不清。

叠加 3.3 的「先写后分类」——provisional 记录从请求**开始**就写——涨速比 r1 的方案更快。

**修法**：把最小形态的条数上限并进分片 4，或在分片 4 的验收里写明「L3 默认关，直到分片 6 的档位开关就位」。

### N8 —— minor（残留） —— TUI 历史面板与 `message.id` 仍未提及

r1 评审第 17、18 条原样保留。两条都不影响裁决，但都是「现在补一句话、以后省一次返工」的类型：

## 五、判定：r2 能不能交用户裁决

### 5.1 结论

**不能原样交。修掉 N1、N2、N3 三条之后可以交，其余（N4–N10）可以在实施期跟进，不构成阻塞。**

理由分两层：

**第一层，硬的**：N1 使分叉 E 的选项文本描述了一个当前代码会静默击穿的能力，而 r2 又把这一项标为「若你只想批一件事，批这个」。**最可能被单独批准的选项，恰好是描述失真的那一个**——这是裁决材料唯一不能出的错，与 r1 那两个 blocker 是同一类：用户读完做出的决定与他的真实意图不符。修法本身很小（改 E1 的内容、上调粗估、写明前置），不需要重写文档。

**第二层，软的但值得一起修**：N2 让 3.4 的容量论证依赖一个没有入口的机制；N3 让分叉 D 在成本上仍是全有全无的二选一，而这个分叉恰恰是唯一一个「用户亲笔写过、我方无权论证掉」的分叉——它的选项形状值得多花十分钟。

### 5.2 相对 r1 的整体判断

**r2 的质量是 r1 的一个量级以上，而且是在正确的方向上提升的。** 具体说：

- 两个 blocker 都真正解决了，不是换个说法绕过去——1.10 单独立节引人写权威、3.1 的 `arrived_at` 附带解释了它为什么不是可选项；
- 主动推翻了自己四条核心假设（1.4、1.6、1.8、1.9），并在每处写明「这条推翻了 r1」，没有把评审发现吸收成自己一贯的主张；
- 新增的分叉 B、C 是真分叉（改 schema、改接口），不是凑数；
- 6.1 按「交付后能回答什么」重排分片，直接回应了 r1「分片 1 不自足」的批评，且新的分片 1（日志 sink）确实自足；
- 3.3「先写后分类」提出了一个我和 r1 都没看见的时序问题，这是评审之外的净增量。

**我在 r1 评审里给的四步建议（补两个分叉、拆一个分叉、改 schema 与选项描述、补三类信息、调分片顺序），r2 全部执行了。** 我这一轮找到的 blocker 不是执行不到位，而是新做的那一项（分叉 E）撞上了一个既有实现的隐患——这类问题只有在真去读 `tui.py` 时才会露出来。

### 5.3 给主会话的建议动作

1. **改 E1**：内容加上「修正 TUI 的 root handler 接管」，粗估上调，选项文本里的「覆盖所有日志行」加前置条件。这一条必须在交给用户之前做。
2. **加 `debug history pin/unpin`** 进 6.1 分片表，并修正 3.4 的「已实现」措辞。
3. **给分叉 D 补 D4**（最小只读 REST 子集，+1 片），改 D3 的代价口径，补「当前无消费者」这一事实。
4. **顺手**（可与 1–3 一起，成本都是一两句话）：修 1.5 与 2.1 的冲突并交代旧库处置（N4）、修 3.1 的悬空引用并给 CLI 面一个落脚处（N5）、附带小项加「默认档位」一行（N6）、把最小条数上限并进分片 4（N7）。
5. **可延后**：N8（TUI 面板 / `message.id`）、N9（三条 nit）、N10（`debug replay`）。其中 N10 我建议至少在附带小项里留一行，因为它是 L2 落地后最便宜的增量，且盘点里手写探针出现了三次。
