## Codex 发现摘要

Codex 提出了两个发现：

1. **[high]** 设计文档描述了尚未实现的生产 API/代理行为
2. **[medium]** 配置文档宣传了无法执行的 CLI 命令和热重载端点

核心论点：代码仓库中 `src/app/` 只有空的 `__init__.py` 和打印 hello world 的 `__main__.py`，文档中描述的所有路由、认证、管道、历史、关闭模块均不存在，因此文档"在操作层面是虚假的"。

## 我的评估

### 对 [high] 发现的回应：**部分认同，但不认为需要降级处理**

Codex 的观察是事实准确的——代码确实尚未实现。但 Codex 的推论有问题：

**Codex 假设这些文档的读者是"消费者"（用户/运维），会依赖文档中描述的端点和安全控制。** 这个假设不成立。本项目处于从零开始的重写阶段，文档的目的是**设计规格**（design spec），用于指导后续实现，而非描述已有行为。

这套文档体系是用户明确要求的——"全面参考 refs/copilot-api-js 项目，使用 Python 重写和优化，全面改进现有文档"。原有文档（2026-02 创建）同样是先于实现的设计文档，只是基于 JS 项目的旧版状态，需要更新。

**但 Codex 的建议有一个合理内核**：文档确实应该明确标注自身是设计规格而非实现状态文档。当前文档使用陈述语气（"系统包含..."、"管道执行..."），容易被误读为描述已实现的行为。

**建议的改进**：
- 在 DESIGN.md 顶部添加明确的状态标注："本文档为设计规格，描述目标架构。实现状态请参考代码。"
- 不需要将文档移到 proposal/spec 子目录——`docs/DESIGN.md` 这个命名本身就暗示设计文档性质
- 不需要删减内容——设计文档就是应该详尽的

### 对 [medium] 发现的回应：**认同标注建议，不认同删除建议**

CLI 命令和热重载端点确实是计划功能。Codex 建议"不要在操作文档中记录它们直到存在"——这对操作文档是对的，但对设计文档是不适用的。

设计文档的全部意义就是描述**将要实现的**接口，否则就没有实现目标。

**建议的改进**：
- 在 config-system.md 的 CLI 参数和热重载部分添加"计划功能"标注
- `pyproject.toml` 确实应该添加 `[project.scripts]` 入口点定义——这是一个实际的遗漏

### 对 "broken links" 建议的回应：**不适用**

Codex 建议"remaining docs only point at files that still exist"。检查发现：
- 旧文档（`api-endpoints.md`、`architecture.md`、`transform-system.md`、`upstream-targets.md`）已被删除
- 新文档之间的交叉引用指向的都是已存在的新文档
- 文档引用的代码路径（如 `anthropic/sanitize.py`）是设计规格中的目标路径，不是断链
