### 2. 带装饰的输出喂给下一条命令，装饰进了比较的那一侧 —— 三实例同日同形态

- `rg -o` 把 ANSI 转义码截进文件名 → `git status -- <不存在的路径>` 全返回空 → 读成「全都干净」；

**落点**：记忆 [[prove-the-probe-ran-before-reading-its-number]] 新增「相邻的一族」整节，含 `rc==0` 本身也可能是假的（2026-08-23 实测 `uv run` 在 `ModuleNotFoundError` 下 `${PIPESTATUS[0]}` 仍为 0）。

### 8. 收尾阶段我自己新造的一条错误解释，而它污染了两位评审的输入

**「同伴 rebase 过 `main`，所以 `56da22a` 变成了 `2248a69`」——这是错的，而且是我在收尾时写下的。**

真相是一次改写事故（另一个会话用 `git rev-parse HEAD` 指认「我刚才那个提交」，中间我的归档提交落了地，于是它改写的是我的提交；CAS 通过，因为传进去的 `<old>` 正是那个刚落地的提交）。归档内容没丢，`git diff 56da22a 2248a69 -- src/.archived tests/.archived` 为空。

**证伪只要一条命令**：本主题另外 11 个提交（`928b355`、`c170f0f`、`28c1a7a`、`1b34815`、`b973ed0`、`c01191f`、`ef4defb`、`598b778`、`1f29d0a`、`fa0b281`、`800eb5b`）的原始 SHA **至今全部在 `main` 上可达**。真 rebase 过的话它们会一起换。**只有一个提交换了身份，那不是 rebase 的形状。**

**为什么它没被任何人抓住**：一个提交换了 SHA，最常见的原因确实就是 rebase。这个解释现成、合理、写下来时不触发任何怀疑，**而它恰好把一次「有人误改了你的提交」的事故描述成了一次例行操作**——失效方向又是单一的：把事故说成常规。

**最值得记的是它的传播路径**：这条错误解释先进了我的会话叙事，再进了 `status.md` 和处置清单，然后**两位独立评审都从我的叙事里读到了它，并各自把它当作事实记进了报告**（评审 A 的 B20／G8、评审 B 的 B10／B20）。**所以在这一点上「两位评审独立地同意」完全不构成佐证——他们读的是同一个被我污染的源。** 独立评审能防的是「作者看不见自己做过什么」，防不了「作者把一件事记错了，而记错的版本是唯一的记录」。

**两份评审报告不改**：它们是点时点原件，改写会伪造记录。活文档（`status.md` 两处、处置清单组 8）已修正。

**落点**：`status.md` 开头 + 「已知的债」两处，本节，以及记忆 [[pin-the-commit-you-rewrite-not-head]]（那份从事故一侧写的描述本来就是对的）。
