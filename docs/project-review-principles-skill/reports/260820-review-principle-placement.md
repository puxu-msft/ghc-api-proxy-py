## 门槛逐条判定

### 门槛 1（发作过不止一次，或一次但代价足以让人记住）——未论证

条目自陈（`:314`）：「同一事故内三次同形（提议进契约面、docstring 断言可重试、docstring 断言客户端未见字节），且第三次是在我已经认错之后由过度修正造成的——满足『一次但代价足以让人记住』」。

**这句话内部就对不上。** 括号里列的第三次是「docstring 断言客户端未见字节」，而紧接着的分句说第三次是「过度修正」。两者不是同一件事：过度修正指的是 `:308` 记的那件——认错后把**实现事实**也从自己的注释里删掉。那是**反向**的失误（撤回时撤过了头），与「把解释写到承诺面上」不同形，条目自己也把它归在「修法方向」而不是「什么算违背」。

**三次里能算独立命中的，最多一次。** 括号里的 (2)(3) 是**同一个 docstring、同一次编辑里的两个句子**（`abb38f5` 的 diff 只动了 `direct_driver/base.py` 4 行）；(1) 与 (2)(3) 的上游成因也不可分——都是把子智能体报告里的那条处方（`docs/tmp/260820-research-upstream-timeout-wiring.md:251`）原样转达、没裁落点。`evolving-skills` 的 `promotion-triggers-on-a-second-hit-not-on-conviction` 把「判独立性看**两次的上游成因是否可分**，不是叙述里用了几个不同的词」写成判据，并**点名**「把同一次事故拆成两条」是要防的绕法（`~/.claude/skills/evolving-skills/SKILL.md:269`）。按这条，本条目是一次命中。

**于是它只能靠「代价足以让人记住」，而代价没有写出来。** 对照同文件其余条目的写法：`:367` 写「用户两次推回、一个新字段、四条测试、一节规范重写」；`:252` 写「405 探针直接证实 + 变异实测证实」。本条目 `:310-314` 通篇是经过叙述，没有一句量化代价。可核的外部事实反而指向**代价有界**：`docs/.human-controlled/config.example.yaml:310-314` 当前只写「这个键约束什么 + 与另两个守卫如何互补」，没有「双重身份」，即那条提议**没有落到契约面上**；修复面是两次文档/注释提交。

**判定**：门槛 1 **未论证**（不是「明确不过」——一次命中加上「被评审当场拦下」的性质，确实可以支撑立条，但必须把代价写成一句可核的话）。这与下面的次要项 M1（缺 `权重` 行）是同一个缺口。

### 门槛 2（复查问题依附本项目结构）——不过

这是我压得最重的一条。条目的「凭什么在这里」`:312` 写：「依附本项目的结构：存在一个用户亲笔、我不得修改的配置契约面，与我的实现面并存。没有这个分层，这条判据无从谈起。」

**这句断言被条目自己的正文证伪，三处：**

1. **四条「什么算违背」里只有一条依赖那个契约面。** `:297` 契约面；`:298` 实现面 docstring；`:299` 把执行点数量说成语义；`:300` 日志行/错误消息/SSE 帧。后三条在任何没有 `docs/.human-controlled/` 的仓库里逐字成立。
2. **「怎么查」的命令一次都不碰契约面。** `:284-288` 的搜索根是 `src/ -g '*.py'`。
3. **正样本对照也在实现面**：`:293` 用 `src/app/pipeline/direct_driver/base.py`。

**核心判据句本身是通用口气的**：`:265`「端点承诺，中间层解释」、`:271` 的腐坏梯度（探针几天、报告几周、`docs/` 几个月、两端以年计）——整段没有一个项目专名，换任何一个有配置文件和日志的项目都成立。

`evolving-skills` 的 `make-the-domain-of-validity-explicit` 正好给了归属探测器（`~/.claude/skills/evolving-skills/SKILL.md:108`）：「一条判据如果在项目 skill 里被写成了普适口气，它多半该上提。」同节 `:112` 的实证②与本例**同形**：判据「探针必须复制生产中会改变被测对象的全部接线」被留在项目 skill 里，理由是「生产接线长什么样是项目知识」，评审指出**那只能决定要列哪些层，判据本身跨项目**，已上提，项目层只留「本项目有哪些层」。

**判定**：门槛 2 **不过**。这是一条通用原则，项目结构只提供了「本仓的两端具体是哪几个面」。

**次生问题：条目一个 user 级 skill 都没引用，而同文件其余四条都引用了。** `:75`→`trusting-a-green-result`、`:97`→`verifying-authoritative-claims`、`:154`→`adopting-agent-findings`、`:244`→`trusting-a-green-result`，写法统一是「一般方法学在 X，本条不重写它」。本条目 `:261-318` 零引用，而它至少有两处踩在既有资产上：

### 门槛 3（能用可跑的检索命令表达判据，且实测过）——不过

命令确实能跑（我按 `:284-288` 原样执行，exit 0，2 行命中：`base.py:230` 免责版、`blocks.py:4`）。问题在召回力，两个层面：

**(a) 同形的第二处就在仓库里，条目自己的命令抓不到。** 我把结局词表原样保留、只把键名换成条目未列入的那批（`client_request_deadline`、`buffer_cap_bytes`、`max_tokens_as_retryable` 等），立刻打出：

```
src/app/pipeline/delivery/blocks.py:20:    """A delivery-side failure. Distinct from an upstream one, which is retryable."""
```

这句与 `abb38f5` 从 `base.py` 里删掉的那句是**同一形态**——断言上游失败「is retryable」，而可重试性由 `upstream_request_retry` 那边的配置决定。条目命令漏它有两个叠加成因：键名表是**手挑的 6 个**（`docs/.human-controlled/config.example.yaml` 里形如 `^\s*[a-z_]+:` 的键行有 95 行），且 `-B4/-A4` 窗口够不着 14 行之外的 `buffering_policy`。

这条发现有双重意义：**它证伪了命令的召回力，同时给条目补上了它缺的第二个实例**（虽然是存量而非新事故）。**注意：我未修改 `blocks.py`，这是留给主会话/用户处置的候选项。**

**(b) 判据的另一半在这份清单的执行模型下无从复查。** `:291` 自陈契约面「不靠命令查——它由『我有没有提议往那里加话』触发，而提议出现在会话里，不在文件里」。这不是「换个命令就好」，是**体裁错配**：

- 门槛 3 的理由写得很直白（`:381`）：「写不出『怎么查』的条目，复查时会退化成凭感觉。」`:291` 给的替代品正是一句自问。
- 更要命的是触发时刻。本文件 `:12` 明写「**不是 always-on 规则**……它要抓的东西按定义是『写的时候看不出来、攒一段时间才显形』的」。而「我正要提议往契约面加话」是**动笔那一刻**的纪律，属于 always-on 体裁。定期复查跑到这一半时，**没有任何动作可做**。
- 事后也补不回来：`docs/.human-controlled/` 整个目录**未被 git 追踪**（`git ls-files docs/.human-controlled/` 输出为空，且未被 ignore），所以那一侧连 diff 都没有，无法回溯「上次复查以来我往那里加过什么」。（这只是陈述后果。按记忆 `dont-escalate-housekeeping-of-user-owned-files`，我不建议、也不提议改变该目录的版本控制方式。）

**判定**：门槛 3 **不过**。回答派活里的那句提问——「一条一半判据无法检索的原则算不算满足门槛 3」：**不算**，而且理由比「检索不到」更重：那一半在这份清单的**执行时刻**上就落不了地。

### B2（召回）命令漏掉仓库里的同形实例，且另一半判据无从复查

### B3（形态）缺 `权重` 行——五条有、它没有

**依据**：`rg '\*\*权重' <该文件>` 命中 `:81 :140 :192 :252 :367`，**六条里五条有，缺的正是被审这条**。这不是体例洁癖：`权重` 行承载的是「这条凭什么被执行、依据强到什么程度」，缺了它，读者在复查时无从判断该不该为它花时间；它同时也是门槛 1 那个未论证代价的落点。**修法**：补一行，形如「**权重：单次命中 + 契约面提议被当场拦下，足以作为暂定复查项执行**——代价是 ⟨具名⟩；**不足以支撑『上面这条命令有召回力』**：⟨见 B2⟩。」

## 次要项

- **M1（形态）缺「命令召回力」自评。** `:83 :194 :252 :367` 四处都有「不足以支撑……有召回力」的自评，被审条目没有。`:281` 的「命令给候选，读一眼多数会排除」谈的是**精度**，`:291` 的「契约面不靠命令查」谈的是**覆盖范围**，两者都不等于召回力自评。并入 B3 一起补。
- **M2（误用风险）`:300` 那条「另一个端点」会被反向执行。** 原文：「日志行、错误消息、SSE 帧里出现『为什么』而不只是『发生了什么』」。下一个人拿它去砍错误消息里的成因（「upstream refused; check your token file」里的后半句）是可能的，而那会直接伤诊断能力。同条目 `:302` 已经给实现面写了「不触发的」子句，这一端没有对应子句。**建议**补一句不触发的形态，例如「如实写出**是什么坏了、下一步能做什么**不触发；触发的是把推导过程与设计理由搬到这一面」。
  另注：这一端**从未在本仓发作过**（`:300` 自陈「这一侧是干净的……列在这里是为了让检查有个反例可比」）。按门槛 1，一条从未发作的判据不该占位置；它作为**对照样本**是有价值的，但应写成对照而不是写在「什么算违背」的列表里。
- **M3（误用风险，派活点名的那句）`:269`「这条原则不收紧注释的厚度」够用，但位置不对。** 判断：**挡得住**「拿这条去砍长注释」这种最直白的误用——它点名了「长注释承担为什么这样写是立过的家法」，措辞明确、用了项目自己的术语，我评估被误用的概率**低到中**。但它在**引言**里，而本文件 `:22`「一次复查怎么走」把复查者直接送去「什么算违背」；`:298` 那条实现面判据旁边没有这句护栏。**建议**在 `:298` 就近重述半句。真正概率更高的误用是另一个方向——**认错后连实现事实一起删**（条目 `:308` 记的就是它），那句护栏目前也只在「修法方向」里，同样不在执行路径上。
- **M4（形态）退役判据可证伪，但覆盖面对不上。** `:318` 只说「`docs/.human-controlled/` 不再作为独立契约面时……本条的结构前提消失」。这是**可证伪的结构事实**（目录取消/配置说明改由代码生成），这一点合格，与其余五条同级。但按此退役会**静默丢掉 `:298 :299 :300` 三条与该目录无关的判据**——正是 `:388`「该原则已被另一条现存条目**完整覆盖**，且做过召回面对账」要防的事。这与 B1 是同一处错配的两个面：条目按「契约面」写依附和退役，按「实现面」写判据和命令。修 B1 时一并修。
- **M5（形态，非本条独有）位置序数正在腐坏。** `:402` 的「后两条」指名的是 `declined-and-adopted-...` 与 `a-broken-test-...`，它们现在是第 3、4 条；`:408` 的「后两条按此办」没带名字，字面读法（第 5、6 条）与原意（第 3、4 条）会给出**不同的合规结论**。成因是清单从四条长到六条，本次新增插在第 5 位是诱因之一（第 6 条由并行的 `5d380a1` 追加，不在本次评审范围）。**建议**把所有位置序数改成 slug 指名，否则加第七条时会再错一次。

## 我可能判错的地方（供主会话权衡）

- **门槛 2 的判定依赖一个类比**（`evolving-skills:112` 实证②）。若用户认为「本仓存在一个我不得修改的用户亲笔面」这件事本身罕见到足以让整条判据算项目知识，那么门槛 2 可以判过。我的倾向仍是不过，理由是**条目自己的命令与三条判据都在实现面**——这不是解释角度问题，是可核的文本事实。
- **B3 与 M1 都是体例一致性**。`adopting-agent-findings:159` 提醒「保持体例一致」属于弱理由。我把它们提到 blocker 是因为 `权重` 行承载的是判据强度而非格式，缺它会直接影响下一次复查是否执行这条；若主会话认为这是纯体例，降级为 major 我不反对。
