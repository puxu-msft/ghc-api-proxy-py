# 已裁决前的提案原件：有损 carrier 处置是否要写入成功响应

> 用户于 2026-09-24 选择仅使用现有安全请求日志／History 损失投影，不新增成功响应头；现行合同仅见 [`../spec.md`](../spec.md) §7.3。下文保留当时的选项和推荐，非当前待裁事项。

## 已确定的边界

活 [`spec.md`](../spec.md) §7.3 已记录用户的默认有损、可配严格拒绝裁决。当前最小实现沿用跨格式翻译的既有 `LossCode.REASONING_STATE_NOT_PORTABLE`，逐个丢弃不可移植的历史 thinking 块，并把路径与原因写入 `conversion_losses` 和安全请求日志。客户端得到的正常 Messages 响应本身目前不包含这一损失说明；此处只问是否需要新增成功响应的可见信号，不重开有损/严格的默认选择。

## 两种可行处置

| 方案 | 收益／适用情形 | 代价与风险 |
|---|---|---|
| A. 仅沿用结构化 request log／History 安全投影 | 复用已有 Loss 机制，运维能按 request ID 定位，Anthropic 响应 wire 无新增字段或事件 | CLI 用户可能看到正常回复却不知道旧 reasoning 被丢弃；“显式”只对运维可见 |
| B. 保留 A，再在成功响应头加稳定的损失 code 与次数（不含内容、签名、session ID） | 调用方可在 HTTP 层看到有损事实；不把诊断文本混入模型内容，也不破坏 Anthropic SSE body | 需要覆盖 streaming 与 buffered、重试后的 response start；一些 CLI 不显示响应头，不能保证用户界面可见；新增外部协议面须先入 Spec |

**建议 B，信心中等。** 默认有损若只写日志，客户端会把变化理解成完整连续性；安全响应头比插入伪造模型文本更诚实。仍不确定主要客户端是否向终端展示自定义响应头，因此 B 是机器可见性而非已验证的人机提示；如果要求 CLI 明示，需要另行裁决客户端侧机制。
