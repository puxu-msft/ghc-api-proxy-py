# 裁决记录

**权威**：`docs/.human-controlled/upstream-retry-and-continuation.md`。本文件不与它竞争——它是用户亲笔的产品裁决，本文件只是**把裁决发生的时间、场合与理由记下来**，供后来者判断某句话的出处与保质期。凡两者不一致，以人写文档为准，并来改本文件。

**为什么需要这份文件**：本主题的裁决大多在一次交互式讨论中做出（2026-08-21），有些已写进人写文档，有些只以口头形式存在于那次对话。独立评审在 2026-08-21 指出，`.dev` 里查不到后者的任何记录，于是把已裁决的内容误判为「照未经裁决的建议施工」。那是记录的缺陷，不是裁决的缺陷。

## 〇、权威文档有两份

`docs/.human-controlled/upstream-retry-and-continuation.md` 之外，2026-08-21 新增 **`docs/.human-controlled/client-side-block-delivery.md`**，它是「客户端块级交付」的权威，本主题的几处判据直接落在它上面：

| 它裁定的 | 对本主题的影响 |
|---|---|
| 完整块的定义：一个 `_start` 与一个 `_end` 事件之间的全部内容；每形成一个完整块就交付并从缓存移除 | 「已交付过完整块」这个判据的定义来源 |
| **响应头在第一次 HTTP 200 尝试时就转发**，不等完整块 | 所以「响应头已提交」**不等于**「已交付完整块」。重放的合法性钉在后者 |
| 后续重试若 HTTP 报错**只能转化为 SSE error**，`Retry-After` 找不到载体转发，接受该限制 | 界定了 D 组那条「429 + `Retry-After`」的适用面：**只在从未拿到 200 时**成立 |
| **响应头提交之后**按 `client_delivery.sse_ping_interval` 发 SSE ping | 直接确认了 ping 不应被「有没有交付过块」拦住 |
| 非流式天然满足块级交付（等价于一次性交付） | 与「非流式只可能无痕重试」一致 |

## 二、只存在于 2026-08-21 那次讨论中的（本文件是它们目前唯一的记录）

下面每条都是用户的明确裁决，**不是本项目的建议**。措辞为转述，括号内是当时给出的理由。

1. **截断块的丢弃规则**：`max_tokens` 时，**只有未完成块就保留它；有任何完整块就丢弃未完成块**。（保留半截内容优于给客户端一个空回答。）
2. **`max_tokens` 一律走合成**，不回落到无痕重试——即使按第 1 条丢弃后一块不剩。
3. **reasoning item 无 `status` 信号时不特殊处理**。（「历史里没有就保持悬念，暂不特殊处理」。）
4. ~~**非流式路径只可能无痕重试，不可能续写。**~~ —— **2026-08-22 用户自行推翻**：非流式应当找到最后一个 incomplete 块的边界，并同样交接。理由是缓冲交付不改变「这一轮没写完」这个事实，客户端仍是唯一能续下去的一侧。已落地（主仓 `af84097`）。
5. **无痕重试不设间隔**，反应式限流器给的间隔除外。（「程序正常运行时多次超长时间的无痕重试是值得的，不必过多防御」。）
6. **`num_messages` 取客户端请求的 `messages` 长度**，不取上游请求。
7. **观测面**：合成之后**客户端请求算成功、本次上游尝试算失败**，请求行用 `[RETY]` 前缀 + 黄色。（「我们有独特的 MCP tool use，所以不难判断」。）`[RETY]` 而非 `[RETRY]`：保持四字符宽。
8. **`stop_reason` 不得被改写成 `end_turn`**，原样透出，已知值着色。（「绝不能」。）
9. **`refusal` 归「无法继续」。**
10. **区分请求断开原因要增强**，理由是有助于调试。
11. **归档去向**：新开主题 `upstream/retry-and-continuation/` 承载归档与后续实现，而非原地归档在 `h2-goaway/` 下。
12. **删码范围**：只删代理内续写机制本身，**其他未接线的功能不要动**。（**2026-08-22 被第 15之三 条局部推翻**：`max_tokens_as_retryable` 已按用户口述删除。`streamReplay` 亦已由第 15 条推翻。其余仍然有效。）
13. **不向上游发真实请求补证**：只查历史，历史没有就保持悬念。
14. **实施顺序**：按 A（文档归档）→ B（删码）→ C（观测面）→ D（无痕重试）→ E（MCP 续写）逐阶段完成，每阶段提交一部分。

## 二之二、2026-08-22 讨论中的裁决

15. **删除 `streamReplay`**：断流重开走 `network` 的普通预算，不设专属计数器。（用户质疑「一条客户端请求最多重开多少次上游流」为什么需要专门配置；本项目答不出好理由——那是代理内续写方案的遗留。）
15之二. **非流式也要交接**，并在翻译时按同一条规则找到被截断 item 的边界（有完整块在前才丢，只有它时保留）。推翻上面第 4 条。
15之三. **配置项 `auto_retry_tool_call_full_name` 从 `client_delivery` 移到 `upstream_request_retry`；`max_tokens_as_retryable` 删除。**（2026-08-22 用户口述，未写进人写文档。**这条局部推翻了第二节第 12 条「其他未接线的功能不要动」**——`max_tokens_as_retryable` 正是那批之一，独立评审据此判为与已记录裁决冲突，因为当时 `.dev` 里查不到这次推翻。此处补记，那条冲突随之解除。）
16. **客户端时限在 body 阶段触发时，发一个 SSE error 帧再收尾**，不直接截断，也不先 flush 缓冲块。（响应头早已发出，状态码改不了；`error_frame` 通道现成、只是没接上。）
17. **D 组照做在 main 上，与同伴的 `fix/upstream-error-events` 分支的冲突留给该分支自己解。**（G1 已停 8 小时、落后 19 个提交、且其独立评审结论为 needs-fix。）

## 三、本项目推论，**不是裁决**（前提变了即失效）

1. **HTTP 状态码类的失败只可能出现在「未交付」位置**，`stop_reason` 类只可能出现在「已交付」位置。前提是「已交付分支不发起新的上游 attempt」。见 `status.md`。
2. **删掉 `synthesized_response_headers_after_sec` 后，`message_start` 只能与第一个完整块同批发出**，半开状态不再可达。前提是该配置项确实被删——**2026-08-22 已随 D 阶段删除**（主仓 `0b57645`），所以这条推论现在成立；它若回来，推论随之失效。
3. **合成时两条上游腿都适用**。由「判据是客户端请求格式」推出；人写文档只写了客户端侧的判据，没有逐腿列举。

## 四、尚待裁决

1. ~~**`max_tokens` 触发合成时 `category` 传什么值**~~ —— **这不是待裁决项，是待对齐项**，2026-08-22 更正。没有分歧：`"max_tokens"` 是上游自己的词，也是唯一候选，实现里用的就是它。需要的是**把这个值告诉改 MCP 端的同伴**，让两边一致。把协调写成裁决是升级过头。
2. **断流重开要不要独立的重试预算？** 用户 2026-08-22 质疑：一条客户端请求「最多重开多少次上游流」为什么需要专门的配置，而不是走标准的上游重试。**本项目认为没有好理由**——`streamReplay` 是代理内续写方案的遗留（当年 replay 与 continuation 并列、各自记账），continuation 删除后配对已不存在。读 body 时撕裂与响应头之前撕裂是同一件事的两个时刻，都是 network 失败；「客户端已经看到什么」决定恢复**合不合法**，不该决定由谁付账。**建议删除 `streamReplay`，断流重开走 `network` 预算，`max_total` 成为整条客户端请求的总闸。** 待用户裁决。

3. **`num_messages` 的判法**：本项目建议按「同一数值重复出现」而非「数值有没有增长」（并行子智能体与主会话共享同一个 MCP server 进程，调用会交错）。**待与 MCP 端对齐**，两边不一致该参数即失效。
