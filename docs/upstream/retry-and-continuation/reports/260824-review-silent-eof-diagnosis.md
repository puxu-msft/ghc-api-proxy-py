### M1 — `upstream_max_gap_s` 被误读为「网线上游静默」

**评审原文**：`inference.py:668-691` 实际测量 pull 间隔且排除末次到 EOF，队列探针得到「本侧暂停 0.204 秒 → gap 0.204、idle 不触发；上游暂停 → idle 触发、gap=None」，因此 168.63 秒不是「第 10 个 chunk 后到 EOF」的间隔，也不能仅凭该字段排除本侧调度、backpressure 或 transport。

**处置：采纳（事实成立），但不接受它蕴含的全部推论。**

我独立复核了 `inference.py:679-692`（HEAD）：`now = time.monotonic()` 取在 `async for chunk in chunks:` 的循环体内，即 chunk **被拉取到本层**的时刻，而拉取节奏由下游消费者决定；循环结束后也确实没有再算一次末段间隔。**评审是对的，我原报告的时间线重建（「收完 10 个 chunk → 静默 → EOF」）写错了**，已改正。

不接受的那一半，理由两条：

1. **该指标对所有流用的是同一把尺**，所以「这条流在这把尺上是 5.3 倍离群点」这个**比较性**结论不受层归属影响，仍然成立。受影响的是**因果解释**（是不是网线上游静默），不是离群性。
2. **本请求的层归属已被 M2 的客户端侧证据大幅收窄**：客户端 transcript 独立显示 08:58:27.792 → 09:01:16.504 之间 168.71 秒未收到任何东西，与本侧记录的 168.63 秒吻合。这排除了「本侧日志字段是记账假象」，但**不排除**「上游在缓慢吐一个永远没合拢的块」——不过 `upstream_chunks=10` 使这个替代解释很难成立（全程只有 10 次到达）。

已在报告中把措辞从「上游静默」改为「本侧两次拉取之间的最长间隔」，并显式写出该指标的层歧义。

### M2 — 报告称客户端结局无法判定，实际可取证，且结论相反

**评审原文**：`~/.claude/projects/-home-xp-src-ghc-api-proxy-py/06dcd6c1-36d4-4204-a630-80c4df8a47a7.jsonl:4900-4901` 已记录同一 `message_id`：08:58:27.792 收到加密 thinking，09:01:16.504 收到 `API Error: upstream stream ended before a terminal event`；这证明实际走 `cut_mid_block` 的 SSE error 分支，而非合成 `incomplete` terminal。

**处置：全部采纳。这是本次评审最有价值的一条。**

我独立复核了那两行（**实测**，`json.loads` 解析，非 grep 目测）：

- line 4900，`ts=2026-08-24T08:58:27.792Z`，`message.id=635ad11c-bc28-4730-a314-f7f929d21692`——与代理落盘的 `message_id` 逐字相同——`content` 只有 `['thinking']`，`stop_reason=None`。
- line 4901，`ts=2026-08-24T09:01:16.504Z`，**另一个** message id，`stop_reason=stop_sequence`，`text` 为 `'API Error: upstream stream ended before a terminal event'`（这是 CC 自己把 API 错误渲染成的一轮助手消息，不是代理发的）。

那句 message 逐字对应 `stream.py` 的 error 帧常量，**不是**合成终结帧的任何一种。故 `cut_mid_block` 为**真**：上游被切穿在某个块中间，而不是停在块边界。

**这条修正的连锁影响比它本身大**：

1. 报告第 5 节「现有落盘无法判定」是错的，已重写。**我犯的是方法错误而不是事实错误**——我自己的记忆条目 `client-transcripts-are-the-last-forensic-resort` 正是写给这种情形的（我方不落盘上行 body 时，客户端 transcript 是最后的取证手段），我没去用它。
