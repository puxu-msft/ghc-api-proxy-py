## F-2：我自己造出了这个功能要防的那个 400

这一条最值得单独写。`will_search` 当时的判据是「识别出了名字」，而历史能认出一个**本请求不再声明**的搜索工具——那时循环里没有任何东西被提升，`defer_loading` 却已经按「有搜索」保留在每个工具上。出站体正是 `req=fcc0bebc` 那次 400 的逐字形状。

**判据从「有没有识别出名字」改成「出站数组里会不会真的有一个 `tool_search`」**。前者是意图，后者是事实，而上游校验的是事实。

评审说触发条件它构造不出（两个一线客户端每轮都重发完整 tools 数组），但没有任何保护、代价是整请求失败、防护成本是一个条件——这三条加起来不需要可达性证明。

## F-3：采纳诊断，不采纳「谁赢」之外的暗示

评审指出的两件事都成立：行为随数组顺序而变，且托管在前时客户端的搜索工具**静默消失**。

已改：托管确定性胜出（它按 `type` 自我标识，客户端那个是启发式），且这个决定移进了 `_search_context`，于是一个答案同时决定 tools 数组、历史渲染、以及交给响应侧的名字——原先它只在 tools 循环里生效，响应侧仍被告知有客户端搜索在飞。

**但客户端的搜索工具不删除**。它作为原本就是的普通 function tool 继续travel。理由：为了给一个客户端也声明了的机制腾位置而删掉客户端声明的工具，正是这个模块的 docstring 写着要防的那件事。**测试断言它活着**，loss 的措辞也改成说实话——第一版我写的是「被托管替代了」，而实际没替代，那是记录在撒谎。这一处是测试先抓住的。

## F-4 与 F-12.1：一条 minor 揭开了一条 major 的另一半

F-4 说 `tool_search_output` 在两条路都没被接住。修完之后，F-12.1 指出守着它的那条测试断言的是「没有块叫 ToolSearch」——而一个空 text 块也满足。收紧成「什么都不该交付」之后立刻变红：**没有名字的 `tool_search_call` 仍在变成空 text 块**，即同一个缺陷的另一半，而我上一轮以为修完了。

现在两者都走显式的 `DISCARDED` 通道。丢弃丢的是模型的一次搜索请求；落到兜底丢的是整轮的可回放性（带空 text 块的 assistant 轮被上游拒收）——后者更贵，这条权衡写进了 Spec。

## F-6：我上一条给用户的话说宽了

评审删掉 `driver.py` 那三行写入，1809 个测试全绿。而我那个「真实端点双向验证」脚本直接调两个翻译函数、写死 `stream=False`——**整条传递链没被验证过，流式那半在真实端点面前一次都没跑过**。我在上一轮的提交信息与给用户的汇报里都说了「双向验证通过」，那句话覆盖的范围比它实际证明的窄。

已补：三条走 `handle()` 与 `assembler_for()` 的测试，两端各做变异确认会红；真实端点验证重做了一次，走服务路径、`stream: True`，客户端收到 `thinking | tool_use:ToolSearch` 且参数完整（`raw/run-tool-search-streaming.txt`）。
