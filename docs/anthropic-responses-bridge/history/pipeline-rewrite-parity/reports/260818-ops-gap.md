### 问题 4：部署形态

| 项目 | 已证实事实 | 差异／缺口 |
|---|---|---|
| 现网 copilot-api-js | 只读 `/proc/926144/cgroup` 为 `0::/init.scope`，cmdline 为 `bun run ./packages/cli/src/main.ts start --restart`，cwd 为 `/home/xp/src/copilot-api-js`；`~/.config/systemd/user/` 仅有 `homebrew.redis.service`，无 copilot／ghc unit。 | 采样时它不在 user systemd service cgroup，且无对应 user unit；证据不足以确定究竟由哪个父进程或终端会话拉起。`--restart` 是其 CLI 启动参数，不等于 systemd 守护。 |
| 现网监听 | 任务基线已核实 `127.0.0.1:4141` 的 IPv4 与 IPv6 listener；只读 `/proc/net/tcp*` 又确认两个 LISTEN inode 与 pid 的 fd `24141006/24141007` 对应。 | 现网是双栈 loopback；不能直接用我们的单栈 basic socket unit 替换而保持监听面。 |
| 我们的 basic systemd 方案 | `contrib/systemd/ghc-api-proxy.socket:5-10` 配 `127.0.0.1:4141`、`Accept=no`、backlog、`http` fd；`.service:9-24` 以专用用户、StateDirectory、`Restart=on-failure`、SIGTERM 和 330 秒 stop timeout 执行 `app start --fd 3`。 | 它实现 socket activation 与服务重启策略，但仅 IPv4，且与现网端口冲突。更关键的是 `cli.py:217-228` 的 `--fd` 分支调用旧 `create_app`，不是 pipeline。 |
| 我们的 rolling 方案 | `contrib/systemd/rolling/ghc-api-proxy-v4.socket:5-10` 和 `v6.socket:5-10` 分别监听 `127.0.0.1:4144`、`[::1]:4144`；generation unit 绑定二者、`Type=notify`，见 `ghc-api-proxy-generation@.service:2-26`；controller 是 restart-on-failure 服务，见 `ghc-api-proxy-controller.service:8-19`。 | 设计上保留双栈 listener 与 generation 生命周期，但端口是 `4144` 而非现网 `4141`；`cli.py:291-301` 的 rolling 入口同样构造旧 `create_app`，尚未把 pipeline 接入可部署的 systemd 路径。 |

**本轮结论：**唯一被直接证实的实时用户契约是 Claude 经 `4141` 的推理服务；外置 UI 和其运维接口是已构建、已编码的强依赖，当前访问证据不足。部署方面，仓库已有两套 systemd 设计，但它们都启动旧 app，故「有 unit」不等于新 pipeline 可被 socket activation／rolling 部署。
