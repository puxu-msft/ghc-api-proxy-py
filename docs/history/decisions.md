## 一、Spec §9 的六项

| # | 事项 | 我的裁决 | 依据 | 推翻的代价 |
|---|---|---|---|---|
| 9.1 | `ProxyConfig.history` 死开关 | **接上**，让 `history.enabled` 真正控制取证子系统 | 本方案正好给了它第一个真实消费者；一个被接受然后被忽略的选项比被拒绝的更坏，而 `cli.py` 自己对 `_NO_HOME_IN_SPEC` 的处理惯例就是「无效就明说」 | 小。改回去只需去掉一处 config 读取 |
| 9.2 | 配置键放哪 | **另立 `forensics.*`**，不复用 `history.*` | 用户裁的是**归档不是淘汰**，而 `history.*` 下的 `success_limit`/`failure_limit` 语义是淘汰。同名不同义比改名更危险——读者会按旧含义理解 | 中。键名进了配置文件之后再改要迁移 |
| 9.3 | 旧链路 history 去留 | **本次完全不动** | `protocol_history.py` 的重复实现在一条不服务生产的链路上，重构 ROI 低；判定它无用并移除触及「不得擅自删除已实现的功能」 | 无。不动就是零成本 |
| 9.4 | 归档物理形态 | **独立分片库文件**（按时间分片的 SQLite 文件） | 让热库始终小、查询始终快——而查询性能是用户点名的硬约束；归档批次可整体移走或离线分析 | 中。形态变了要重写归档器与 `/archives/*` 端点 |
| 9.5 | replay 是否记录自身 | **记**，但标记 `origin=replay` 与被重放的源 id | 不记的话重放产生的上游交换会变成一条无来源的记录，比不记更难解释；标记使它可被过滤 | 小。加一列、查询默认过滤 |
| 9.6 | L1 与 `requests-*.jsonl` 的关系 | **并存，JSONL 不再扩字段** | 两者服务不同问题：JSONL 是常开的、无依赖的、grep 得动的完成记录；L1 是可 SQL 查询的父行。让 JSONL 承载 L2/L3 的父子结构是把它变成一个坏数据库 | 中。若改为「L1 从 JSONL 派生」，采集点要重设计 |

## 二、优先级重排 —— 已于 2026-08-21 被再次推翻，见第五节

（原文保留作记录：曾裁决「把 L2 提到最前」，依据是一张缺口表。那张表随后被证明对 L2 也没做「是否已被同伴解决」的核对。）

**裁决：把 L2 提到实施顺序最前，分片 1、2 的结构化日志降级为架构性改进。**

依据是需求盘点的重新计分。同伴 2026-08-20 合入 `request_log_file.py`（`10e4811`）之后：

| 缺口 | 被点名次数 | 现状 |
|---|---|---|
| 实际发往上游的字节级 body | 4 | **仍未解决** → L2 |
| 该次请求的服务端完成记录 | 3 | **已被独立解决** |
| 上游 SSE 帧时序 | 3 | **仍未解决** → L3 |
| 上游错误响应体原文 | 2 | **仍未解决** → L2 |

仍未解决的三个缺口全部落在 L2 与 L3 上，其中 L2 覆盖两个、且是唯一被点名 4 次的那个。

**这项裁决改动了用户 2026-08-20 已经看过的分片顺序**，所以它是本文件里最该被审视的一条。反对它的理由是成立的：proposal §6.1 把 L1 排在前面是**结构性理由**（L1 是 L2/L3 的父行），不是紧迫性理由。**我没有改变父子依赖**——L1 仍然先于 L2 落地，只是不再为「补第二大缺口」而存在，且分片 1、2 的结构化日志从 L1 之前挪到之后。

修订后的顺序：

## 三、Spec 覆盖不到分片 7、8 的问题

Spec §10.3 指出：proposal §6.3 说「把第三节扩写为 Spec」，而第三节完全不涉及结构化日志，所以这份 Spec 覆盖不到结构化日志那两片。

**裁决：不并进这一份，让它们用 `reports/260821-structured-logging-design.md` 作为规范来源，在实施前补一份短 Spec。** 依据是两者的验收方式根本不同——取证记录的验收是数据对不对，终端呈现的验收是人看着对不对，把它们冻结在同一份文档里会让「冻结」这个词对其中一半失去意义。

## 四、`request_log_file.py` 同步写盘的问题

Spec §10.1 指控它是同步的、跑在事件循环上，与用户点名的硬约束冲突。

**裁决：本次不改它，但记为已知缺陷并在 L1 落地时一并评估。** 依据：它是同伴刚合入的生产代码，不在本任务范围内；且实际影响量级尚未测量（正在由事实评审核实）。**若评审测出它的单次写入代价确实显著，我会把它提为一个独立的小修，而不是塞进 L1 那一片。**

## 五、重定范围（2026-08-21，取代第二节）

### 触发这次重定的事实

对**当前生产 import 闭包**做了一次全面重测（不是逐项猜），结果：

| 缺口 | 被点名次数 | 现状 | 证据 |
|---|---|---|---|
| 实际发往上游的**字节级** body | 4 | **部分解决** | `rejection_capture.py` 在 `UpstreamRejected`（4xx 非限流）时写 `payload: context.payload`——**翻译后的字典，不是序列化字节**；成功、5xx、超时、前序 attempt 均无。全仓对 `response.request.content` 只取 `len()`（`pipeline_app.py` 与 `handler.py` 各一处），字节从未保存 |
| 该次请求的服务端完成记录 | 3 | **已解决** | `request_log_file.py`（`10e4811`），常开、在生产闭包里 |
| 上游 SSE 帧**时序** | 3 | **部分解决** | `trace.first_upstream_byte_s` 已记首字节延迟；**逐帧到达时刻仍无**，所以「流中途停了多久」答不了 |
| 上游错误响应体原文 | 2 | **已解决** | `rejection_capture.py` 的 `upstream: error.body` |

两个全解、两个半解。**这不是同伴抢跑，是同一批事故催生了两条独立应答**——`rejection_capture.py` 的 docstring 逐字点名了我调查过的那两起（`The use of the web search tool is not supported.`、`messages: text content blocks must be non-empty`），并写下「the investigation had to reconstruct the outbound request from the *client's* own transcripts」。

### 裁决

**剩余真实增量只有两样**，其余不做：

1. **出站字节级保真**：保存 `response.request.content` 的**实际字节**，覆盖所有结局（成功、4xx、5xx、超时）与**每一次 attempt**，而不只是被拒的那一次的翻译后字典。
2. **逐帧到达时刻**：在 `_counted_upstream` 旁路记录每个原始 chunk 的到达时刻与长度，答「中途沉默了多久」。

**不做**（原十片计划中被本次重定移除的）：

| 原分片 | 不做的理由 |
|---|---|
| L1 独立落盘 + `entries/list`/`get` | 完成记录已由 `requests-*.jsonl` 承担。可 SQL 查询是便利性收益，不足以支撑一套新表 + 路由模块 + 端点契约 |
| 结构化日志承载、TUI 改消费者 | 与取证已无因果（完成记录已落盘）。它仍是一项合理的架构改进，**移入 deferred**，由 `260821-structured-logging-design.md` 承载 |
| 会话聚合 + 归档 + `sessions/*`/`archives/*` | 数据量已大幅缩小（不再有 L1 全量表），归档的前提不再成立 |
| `export-cassette`、`replay`、WS 推送、pin/unpin | 全部建立在「有一套完整的取证库与查询面」之上，那个前提已被移除 |
| 17 个配置键、10 个指标、`ChunkSpool` | 评审已判为镀金；重定范围后更无立足之地 |

**HTTP 查询面怎么办**：用户 2026-08-20 裁决要「完整 HTTP 支持」，那是针对当时那套完整取证库的。重定范围后没有库可查，该裁决的前提消失。**记为待确认**：若仍要 HTTP 查询面，它的对象应是已有的 `requests-*.jsonl` 与 `rejected/*`，那是另一件事，不在本次实施内。

### 这项裁决最该被推翻的地方

「可 SQL 查询不足以支撑一套新表」是一个**价值判断**，不是事实判断。若你认为「能按 model/session/时间窗过滤地翻历史」本身就值那套基础设施，那么 L1 应当恢复，本节的其余移除项也要跟着重新评估。我倾向不做，是因为项目明确反对不成比例的基础设施，而 `jq` 对 5,000 行 JSONL 足够用。
