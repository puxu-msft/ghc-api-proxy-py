## 用户裁决

- 用户首先要求“分析并支持 HTTP 499 retry”，裁决 499 应支持 retry。
- 用户随后要求“你直接并入但不提交该文件，我再审核”，授权 agent 把已评审候选转录到目标工作树，并保留最终审核权。
- 用户审核后接受需求修订，并把目标文档收敛为 `499 Client Closed Request` 一项；用户明确说明，候选中的详细解释本身正确，但不应该放入该文档。
- 对于本轮 `.dev` 候选和评审材料，用户选择专用 `origin/dotdev` 分支持久化。该选择只授权创建并首次 push `dotdev`，不授权 push `main` 或其它 ref；storage procedure 的权威在 `.dev/README.md`。

## 采纳到需求层的内容

目标 Spec 的“这些情况下一般可以继续”列表增加：

- 499 Client Closed Request

这条精简要求是用户控制 Spec 中的权威内容。代码与测试负责实现和转录该要求，不把实现策略反向提升成需求。

## 未放入目标 Spec 的内容

候选曾给出 `serverError` mapping、两级预算、deadline/draining、error envelope、rejected capture、observability、生产观测和未采用方案的详细解释。用户确认这些解释正确，但裁决它们不属于该需求文档。

这些内容没有被删除或伪装成未采纳的行为，而是按其信息层级迁入 `.dev/docs/upstream/retry-and-continuation/http-499-retry.md`：那里是 implementation/specification understanding 的活载体；`status.md` 只报告当前实现和执行状态；本文件只记录候选如何被用户处置。

## 评审历史

本候选在用户审核前经过初评、限定复评、closeout review、用户裁决整合评审及限定复评。报告 originals 位于 `.dev/docs/upstream/retry-and-continuation/reports/`，所有 finding 的终态和未采用路线以 `review-disposition.md` 为权威。
