### 4.3 这个空块的两项危害

**危害一：这个 turn 会在被重放时被上游拒绝。** 项目自己实测记录：上游对携带空 text 块的 assistant turn 返回 400 `messages: text content blocks must be non-empty`，对 `content: []` 返回 200（`translation_driver/responses.py:109`，实测 2026-08-20，`exp/260820-empty-text-probe/` F3/F6/F4）**[PROJ]**。`ResponsesAssembler` 自己也两次写下这条理由，正是它拒绝让 `tool_search_call` / `tool_search_output` 掉进兜底的原因（`openai_responses.py:518` 与 `:390-391`）**[CODE]**。也就是说：**项目已经认识到兜底分支会产出「重放即 400」的块，并为两个具体 item type 单独绕开了它——但没有修兜底本身。**

**危害二（我认为这条更严重，且此前没人写下来）：`stop_reason` 会说谎。** `_close` 第 576-577 行只在 `draft.kind == TOOL_USE` 时置 `self._saw_tool_call = True`；未知 kind 走不到那里。于是 `_read_terminal` 第 650 行算出 `stop_reason = "end_turn"`。**客户端被告知模型正常地把话说完了，而实际上模型发起了一次工具调用并在等结果。** 客户端不会去执行工具，也不会回传结果，这一轮就此中断且看不出中断。**[CODE]**

### 4.4 Anthropic 客户端今天是否受影响

**就 `custom_tool_call` 而言：今天不受影响。** 该 item 只在客户端于 `tools[]` 声明了 `{"type": "custom"}` 时才可能出现（§2.1、§5.3），而 Anthropic Messages 协议的工具声明形态是 `{name, description, input_schema}`，没有 custom tool 的拼法；翻译层 `_function_tool`（第 181-186 行）会把 `input_schema` 改写成 `parameters` 并补 `type: "function"`，产出的永远是 function tool。**[CODE]** + **[INFER，置信度高]**

**但它与 Responses 腿共享同一个兜底缺陷，且失效模式更隐蔽。** Responses 腿的表现是 200 已发出后流被撕断——响亮、有栈、进了 issue。Anthropic 腿的表现是一个空块加一个错误的 `stop_reason`——不报错、不告警、日志上看是一次成功的交付。**同一个缺陷，在主产品路径上比在报障路径上更难被发现。**

Anthropic 腿今天真正的暴露面在 §5.3 的「上游可主动产出」那一类，尤其是 `additional_tools`（见 §5.3 的风险标注）。

### 4.5 一个尚未爆发但已经埋好的形态

上面第 4.2 节走通是因为 `draft.text` 恰好为空。**若某个未知 item type 的内容恰好经由 `response.output_text.delta` 累积**（`push` 第 449 行对 `output_index` 匹配的任何 draft 都会累积，不检查 draft 的 kind），`draft.text` 就非空，于是 `content_block_start` 会带着**完整正文**出去，而 `_delta_for` 仍返回 `None`，**没有 delta**。Claude Code 从 delta 读内容——`anthropic_messages.py:72-73` 正是为 thinking 的同一问题写的 shim：「upstream puts the signature inside `content_block_start` and never sends a delta for it, and Claude Code reads it from the delta — so without this the signature is present on the wire and still lost」。**[CODE]** + **[PROJ]**

也就是说：这条路径上内容会**出现在线上却读不到**。标为 **[INFER，置信度中]**——机制清楚，但我没有构造出一个真实会这样累积的 item type，也没有实测 Claude Code 对非空 `content_block_start.text` 的处理。

## 5. 缓冲（非流式）侧

### 5.1 处理方式：丢弃 + 记录，不崩溃 **[CODE]**

`src/app/pipeline/translation_driver/responses.py`，`from_openai_responses_response` 第 193-200 行：

```python
_, blocks = blocks_from_item(item, client_search_tool=client_search_tool)
for block in blocks:
    if block.kind is BlockKind.UNKNOWN:
        response.conversion.record(
            LossCode.ITEM_NOT_CARRIED, f"output item {item.get('type')!r}"
        )
        continue
    response.blocks.append(block)
```

`blocks_from_item`（`translation_driver/openai_responses.py:448-519`）对 22 个兜底 item 全部落到第 519 行 `return "user", (ContentBlock(BlockKind.UNKNOWN, raw=item),)`。于是缓冲侧：**块被丢弃，损失被记入 `Conversion`，响应正常交付。**

### 5.2 与流式**不一致**，三处，逐项对照

| | 流式 `ResponsesAssembler` | 缓冲 `blocks_from_item` + `from_openai_responses_response` |
|---|---|---|
| 未知 item 的内部表示 | `kind = <item type 字符串>`，与 `TEXT` payload 矛盾 | `BlockKind.UNKNOWN`，**有一个专属的名字** |
| 交付给 Responses 客户端 | **`ValueError`，流被撕断** | 丢弃，正常交付 |
| 交付给 Anthropic 客户端 | 静默空 text 块 | 丢弃（不产生空块） |
| 是否留下记录 | **无**（既不 log 也不记 Conversion） | `LossCode.ITEM_NOT_CARRIED` |
| `stop_reason` | 受影响（`_saw_tool_call` 不置位，见 §4.3） | 同样受影响：第 202 行 `has_tool_call` 由 `response.blocks` 算，被丢弃的块不在其中 |

**缓冲侧的设计是对的，流式侧是错的。** 缓冲侧有 `BlockKind.UNKNOWN` 这个专属值把「未识别」和任何一种已知内容彻底分开；流式侧没有对应的东西——它有 `DISCARDED`（`openai_responses.py:391`）表示「认识但故意不投递」，却没有一个表示「不认识」的值。第 390-391 行的注释亲口划出了这个区分并把兜底那一半留空了：

> A draft kind meaning "recognised, and deliberately not delivered". Distinct from an unrecognised item, which falls through to the text fallback and reaches the client as an empty block — a shape upstream refuses when the turn is replayed.

**修法的方向由此确定**：流式侧需要一个与 `DISCARDED` 并列的 `UNKNOWN` draft kind，`_close` 对它的处置与缓冲侧看齐（丢弃 + 记录），而不是去放宽 `ResponsesFramer.block` 的 raise。这样两条交付路径重新对同一个事实给出同一个答案——这正是本仓库反复付过学费的那条（`fef7d96` 的记录，见 `responses.py:39`）。

顺带：`stop_reason` 说谎（§4.3）在**两侧都成立**，不是流式独有的。修兜底时要一并处理，否则修好了块的去向，仍会告诉客户端「模型说完了」。
