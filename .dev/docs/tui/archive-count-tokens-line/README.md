# 档案：计数请求那一行，与「修好一层会在上一层重演」

起因是一条读不出来的日志，用户贴出来问「为什么只有这些信息，却 200」：

```
[ OK ] 17:08:01 H1 200 anthropic-messages/claude-opus-5 1.2s ↑19.7k
```

当前行为以 `../spec.md`「一次计数请求怎么读」为准。本文记的是**为什么这样定、以及路上踩了什么**。

## 零、最该记住的一条：修好一层，往往在上一层重演

这是 `../archive-truncated-stream/` 那条「缺席读不出来」的续集，而且是更难发现的形态。

第一层：`/v1/messages/count_tokens` 是**唯一一种没有回复的 200**。没有块、没有结束原因、没有下行词元；成功行又把 `METHOD /path` 折叠成 `<inbound-format>/<model>`，而计数与真实对话共用同一个 inbound format。每一处缺席都诚实，合起来读者却分不出「一次计数」与「一次交付成功却丢光回复字段的轮次」。

第二层：补上「谁给的这个数」之后，`local` 这一个词又同时代表三种结局——**这条路由本来就没有上游计数器**（正常配置，天天发生）、**上游被问了却答不出**（事故）、**运维配成只估算**。

于是同一个缺陷换了层：**失败并没有从行上缺席，它穿着正常情形的衣服**。前者是「什么都不显示」，后者是「显示得和最常见的正常情况一模一样」——后者更难发现，因为它**有输出**。

**可复用的判据**：给一个「读不出来」的问题补上字段之后，立刻再问一遍**这个新字段本身**——它的每个取值是否只对应一种结局？某个取值同时覆盖正常与异常，就说明这一层还没修完。

## 一、两处各答一半

`↑19.7k` 是**词元不是字节**（字节必带 `B`/`KB`/`MB`，裸的 `k`/`m` 是词元），没有 `↓` 是因为计数没有输出词元，没有字节字段与第二条协议腿是因为 count 分支在 delivery 路径**之前**就 return 了，而那些字段只在 delivery 路径上填。

- **「这是一次计数」由格式前缀说**：`anthropic-messages-count-tokens/<model>`。它是**端点**，比计数器早一步知道，所以一次连计数器都没跑到的计数仍然说得出自己是计数。
- **「数字是谁给的、之前试过谁」由行尾 `provider(...)` 说**，占据结束原因的槽位（计数没有结束原因，两者不可能同时出现）。

## 二、上游那一腿的含义比想象的窄

它说的是上游**给过响应**，不是「上游答出了这个数」。这个区别是被实测逼出来的，不是想出来的——见第五节。

| 行 | 含义 |
|---|---|
| `H1/H1 … ↑<字节> ↓<字节> ↑<词元> provider(ghc)` | 问了上游，上游答了 |
| `H1/H1 … ↑<字节> ↓<字节> ↑<词元> provider(ghc-failed,local)` | 问了，**回了响应但答案不可用**（200 却无可用 `input_tokens`、或 body 非法 JSON），降级估算 |
| `H1 … ↑<词元> provider(ghc-failed,local)` | 问了，**连响应都没给**（错误状态被抬成 pipeline 错误、传输失败） |
| `H1 … ↑<词元> provider(no-counter,local)` | 这条路由本来就没有上游计数器（翻译到 `/responses`），从没问过 |
| `H1 … ↑<词元> provider(local)` | 运维把 `providers` 配成只估算，或把 `local` 排在 `ghc` 前 |

括号里是**按发生顺序的轨迹**：试过而没答上的在前，真正应答的在后。

真正的 *refusal*（`ProviderError`：未知模型、能力缺失）不走这里——它一路冒到 400，既不是 200 也不带 `provider(...)`。

## 三、判据要选在有事实的那一层

降级原因由 `handle_count_tokens` 判定，不在展示层解析字符串：依据是它自己传给 `count_tokens()` 的 `upstream_absent_reason` 字面串，以及尝试轨迹里有没有 `ghc:` 开头的条目。

**不能只看「这条路由有没有上游计数器」那个布尔**——运维还能通过 `providers` 的裁剪与排序让上游根本没被问，那既不是缺计数器也不是失败。这是差点写进去的一个谎。

## 四、不着色，理由是「常见即噪声」

裁决 2026-08-20，用户明确选了不着色。`ghc` 与 `local` 都不是「有多成问题」的档位：一条翻译路由天天答 `provider(no-counter,local)` 是正常配置而非事故，给它警示色等于每天喊一次狼来了。降级那一档改由**词**承担而不是颜色——这样它在**落盘日志里同样读得出来**，颜色在那里是丢失的。

## 五、已否定的方案与否定的理由

- **`count(ghc→local)` 箭头写法**（我提的，还标了「推荐」）——用户否决，选了把原因写进括号。后又从 `count(...)` 改名为 `provider(...)`：格式前缀既然已经带上了 count-tokens 端点，这个槽位再说一遍「这是计数」就是重复，它该说的是谁应答的，也就是 `providers` 配置里的那个词。
- **用 `upstream_counts` 布尔判定降级原因**——见第三节，会撒谎。
- **把「为什么是估算」推迟掉**（我判为「可选、非本次引入」）——用户一句质疑推翻。那个推迟判断本身是被否决的路线：它把「同形」误当成了「非本次引入」。
- **只在结构化记录里带 `count_tokens_attempts`、控制台行不动**——作为最便宜的一档提过，用户选了更重的方案（原因上行）。更细的原因（超时还是 500）至今仍只在那条轨迹里且无读者，见 `../deferred.md` 第 4 条。
- **注释断言「上游拒绝就不会在行上留下腿」**——被评审用探针证伪，见下节。

## 六、被证伪的因果解释

我在 `handler.py` 注释里写过「上游拒绝时不会留下腿，所以 `count(local)` 是唯一说明估算的东西」。评审构造了反例：**上游 200 但 body 无可用 `input_tokens`**——两行 extras 已写入，随后才抛错降级，于是腿在、计数仍是 `local`。实测行形如 `H1/H1 … ↑77B … provider(ghc-failed,local)`。

行为没改（这条行其实比注释更诚实：上游确实被问了、确实答了、只是答的不能用），改的是注释，并补了测试 `test_a_count_upstream_answered_uselessly_keeps_the_leg_it_flew` 把反例钉住。

**上游腿只报了一半**也是评审抓的：只记了 `bytes_in` 不记 `bytes_out`，于是同一条行上复现了本次要修的毛病——读者看到 `↑77B` 无 `↓`，按这条行的约定推出「上游什么都没回」，而上游回的恰恰就是行上那个数字。

## 七、两次证据作废（收尾时，与本功能无关但更值得记）

两轮独立评审各自抓到一次，第二轮复评又抓到**同一族错误在更正里复发**。这三条与 TUI 无关，但都是「判据的载体被挪出了被测命令」这一族：

1. **共享树上的相对引用是移动靶**。`git worktree add --detach <path> HEAD~2` 落在了与对照组**同一个提交**上，因为同伴在两条命令之间推进了 HEAD（实测 `main` 一小时移动四次）。于是「两个点位」实为一个点位测两遍，**没有任何命令失败**。重做时改用显式 SHA，并把比较从计数升级为**失败集合**（`comm` 双向差分）。
2. **命令旁边硬编码结论**。核对活文档残留时连续两条 `rg` 都是坏的，而同一行的 `echo "(空=无残留)"` 两次照印。**两次报错都大声打在上面**——不是失败不可见，是报错在上、自写的结论在下，眼睛停在最后一行。
3. 顺带纠正一个机制解释：不是「`-F` 不带参数」导致 pattern 落到路径位，而是**一旦用 `-e` 提供模式，位置参数就全部变成路径**（`/tmp` 对照实测：单用 `-F` 完全正常）。这句错的解释当时已写进四处。
