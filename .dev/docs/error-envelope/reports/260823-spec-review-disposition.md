# 错误信封 Spec：评审处置

**这份是处置记录**，答「评审提了什么、采纳了哪些、为什么」。评审原件是点时点记录，不改：[260823-spec-review-gpt.md](260823-spec-review-gpt.md)。Spec 当前状态见 [../spec.md](../spec.md)（v3）。

**一句话**：4 条 blocker、8 条 major、1 条 minor，**13 条全部采纳**，无驳回项。Spec 从 v2 改写到 v3。

## 为什么没有驳回项

这不是省事，是逐条看下来确实都成立。其中三条是我自己写下的错误，值得单独说：

### F-01 我给用户的裁决开了一个例外

v2 §5 写「上游的失败事件必须映射到 `ErrorCategory`（**直连也要**）」，理由是「本代理已经在重新成帧，谈不上原生透传」。

**这是把实现约束反过来改写了用户的行为裁决。** 裁决第 1 条说「直连路径一定用原生的」，没有给流内事件开口子。而且那个理由本身站不住——`event: error` 是自足的 SSE 事件，不是内容块，不需要装配，原样转发在技术上完全可行。评审说得对：「若作者认为块级交付让直连原生事件不可实现，应把这个真实冲突交回用户裁决，不能自行宣布『谈不上原生透传』」。

我连那个前提都没有验证就宣布了。v3 §3.4 删除该例外。

### F-04 我把待裁决项写成了实施指令

v2 §7 的标题、开篇、三个候选都承认这项尚未裁决，最后一句却是「在裁决到达之前，实施按第 1 个进行」。

这正是项目记忆 `restating-a-text-drops-its-qualifiers` 记的那个方向——**总把「需要裁决」转述成「已获授权」**。区别只在于这次发生在 Spec 自己的实施命令里，而不是在转述权威文档时。评审在核对权威引文那一节明确写了「§1 的转述没有发生这个错误；真正发生该错误的是 §7 最后一段」。

v3 §10.1 删除该句，改为「在裁决到达之前，不实施依赖这一格的任何公共行为；不依赖它的结构性部分可以先做」。

### F-05 我给用户亲笔的名单加了原文没有的限定

v2 §3 写「该黑名单是为成功响应写的，是否逐字适用于错误响应须在实施时核实并登记」。**`message-format-reshape.md` 的「客户端返回 Anthropic Messages」一节没有成功／错误的区分。** 我凭空加了一个限定，然后用它把一件会直接影响客户端重试与排障的事（`retry-after`、rate-limit、request-id 头）推给实施期临场决定。

v3 §3.1 删除该限定，明写沿用同一份直连黑名单。

## 我自己另外做的两处收窄（不在评审发现里）

- **v3 §5.1 原写「Anthropic 真实 API 对未知模型答 404 `not_found_error`」**——仓库里没有这个观测，我是凭印象写的。已改为只用本代理自己的语义论证（模型不在目录里就是没找到），并明写「不以 Anthropic 真实 API 也这样答为据，我未验证」。
- **`ErrorCategory` 新增成员时保留现有 6 个的拼写不变**，因为 `hand_over.py` 与 MCP 侧已在读这些值（契约在 `.dev/docs/upstream/retry-and-continuation/decisions.md` 4.1）。这一点 v2 已有，v3 保留并写明理由。
