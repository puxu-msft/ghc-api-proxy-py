## 建议修订

在“这些情况下一般可以继续”列表中，于“429 Too Many Requests”之后增加：

- 499。这里的 499 是上游对本代理已经完整发送的请求作出的 HTTP 响应，不代表本代理观察到下游客户端已经断开。

在该列表之后增加：

HTTP 499 按现有 `serverError` 策略处理：只要尚未向下游交付响应、服务未进入拒绝新重试的 draining 状态、请求与尝试 deadline 尚未终止流程，并且 `upstream_request_retry.strategies.serverError.max_retries` 与共享 `max_total` 均仍有预算，就原样重放同一请求；不增加 499 专用计数器，也不增加冷却间隔。

如果 499 的重试预算耗尽或重试被 draining 状态拒绝，`PipelineAbort.cause` 保留最后一次上游 499，随后由既有 error envelope 按 direct/translated 路径以及 upstream source bytes 是否非空来呈现该失败：保留 499 status 与可转发响应头；仅在 direct 且 source bytes 非空时原样传递 upstream body，translated 路径或 observed empty body 则写客户端格式的错误 envelope。

作为可重试的瞬时上游失败，499 不再作为确定性请求拒绝写入 rejected request capture。既有请求记录仍写最终尝试总数；请求头阶段被成功 retry 替换的 499 failure category 当前不会单独进入 `replaced_failures`。

本条款一旦并入，`src/app/model_provider/ghc_client/errors.py` 的 `RETRYABLE_STATUSES` 与 `tests/unit/model_provider/ghc_client/test_http_499_retry.py` 即是它的转录；条款变化时必须同步更新两处转录，发生冲突时以当前用户控制 Spec 为权威。

## 修订依据

2026-09-03 的生产 capture 显示：上游在单次请求约 123.1 秒后返回空体 HTTP 499，本代理已经向上游发送 2,859,854 bytes，但还没有向下游交付响应，最终记录 `attempts=1`。修复前仅因 499 不在 `RETRYABLE_STATUSES` 中便把它归一化为 `UpstreamRejected`；这使它绕过已经存在的透明重试 driver 与预算，并不来自一次下游断开观测。

这些事实只支持“此处 499 不应被解释成本代理观察到下游已经断开”，不支持断言 GitHub Copilot 为何产生 499。请求体较大与约 123 秒延迟是相关观测，不作为重试判定条件；若其中任一观测后来被证明与 499 成因无关，“499 应支持 retry”这一用户裁决不变，调用链证据只决定实现落点。

## 未采用的方案

- 不把 499 放入 `network` 策略。它是一个已经收到的 HTTP 状态，而现有 `network` 策略用于 timeout、连接失败及其他无状态失败；放入 `serverError` 保持有响应的瞬时失败使用同一预算。
- 不新增 `http499` 专用配置。现有 `serverError` 的独立预算与共享总预算已经完整表达次数上限；新增配置只会制造另一个必须维护的策略面。
- 不在 driver 中直接判断 `status_code == 499`。生产 SDK 会先把 499 抛成 `APIStatusError`，错误归一化边界才负责决定它是可重试上游失败还是确定性请求拒绝；在 driver 特判会让 rejection capture、错误透传与 retry classification 对同一状态产生分裂。
- 不为 499 建立独立 error body 透传规则。预算耗尽后的 499 仍受通用 direct/translated error envelope 约束，避免同一 upstream failure 因 status 特判而产生第二套 wire contract。
- 本次不扩展 header-stage retry observability。现有 `attempts` 已记录重试总数；增加每次被替换 failure 的持久化属于独立可观测性改动，不是支持 499 retry 所必需的控制流变化。
